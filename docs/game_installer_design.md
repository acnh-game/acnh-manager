# 通用游戏安装器与 agent 管理器(1.1.0)

## 1. 定位与范围

**新定位**:ACNH-Manager 从"agent 安装器"扩展为"**Switch 主机的通用安装器 + agent 管理器**"。
安装器支持任天堂官方包与官方包的各种封装形式(**NSP / NSZ / XCI / XCZ**),**来源由用户提供**,
我们**不再托管任何游戏内容,也不在清单里放任何下载地址**。

**目标用例**:

1. 用户自己的游戏版本低于我们支持的版本(例如只剩 1.0.0 基础版, 或者安装了旧的 upd 包的 2.0.0 版本):他自己准备 3.0.3 更新包,
   通过"手机浏览器上传"或"给一个下载地址"装上 → 门控变 `supported` → 他再装 agent;
2. 机器上**根本没有装这个游戏**:首页提醒"可以用本应用的安装功能装一份游戏本体";
3. 通用用途:没有电脑在身边时,用手机开热点 + 手机自带浏览器,把 `nsp/nsz/xci/xcz`
   传进主机并安装 —— **手机浏览器不支持 WebUSB 这类 USB 设备 API**(参考实现里那套 `tools/webusb`
   在手机上不可用),所以这条需求只能靠 HTTP 解决,这也是本方案选 HTTP 而不是 USB/WebUSB 的原因。

**边界(明确决定)**:

| 范围 | 决定 |
|---|---|
| 内容来源 | 三种:**本机 SD 文件**、**HTTP 下载**(主机作 client)、**HTTP 上传**(主机作 server) |
| 我们托管什么 | **什么都不托管**:不发布游戏包、清单里没有下载地址 |
| 支持格式 | **NSP / NSZ / XCI / XCZ**;允许装游戏本体(XCI 需要翻转 NCA 头的 distribution type)、更新包、DLC。**NSZ/XCZ 里大的 NCA 是 NCZ 流**(NCA 头原样 + 分节表 + 可选块表 + 负载,分节数据是"已解密"的),按 `install/ncz.*` / `install/ncz_decode.*` 还原成 NCA 之后再写占位:有块表时按块走(压缩块是各自独立的 zstd 帧,**压不小的块原样存放**、直接拷贝),没块表时整段就是一条 zstd 流;分节里带 key/counter,`crypto_type >= AES-CTR` 的节要用 AES-CTR 加回去(规则与判据逐条照参考实现的 NCZ 读侧)。**一个容器里有几份 meta 就装几份**(整合镜像"1G+1U+2D"那类):每份 meta 各自写记录,照参考实现的 `InstallInternal` 那样循环;只装本体那份会让更新与 DLC 从头到尾不落地(第 14 节第 33 条) |
| 校验与安装选项 | **逐项跟随参考实现的默认值**(`include/app.hpp`):装到 SD、已装则跳过、不允许降级、**默认跳过 NCA 哈希与 NCA 头验签**、不忽略 distribution bit(即会改造它)、票据相关默认值见第 5 节 |
| 与 agent 的关系 | **一次动作做两件事**:装完本体/更新、且落地的版本受支持时,自动把 agent 装上(第 14 节第 32 条);追加内容、数据补丁、不受支持的版本都不触发 |
| MSP(mod 包) | **不做**(理由与影响见第 7 节) |
| 不做 | 不卸载游戏、不卸载更新包、不修改存档;也**不做多文件队列**(一次只装一个文件)。**曾经**写在这里的"不做 agent 与游戏安装的合并动作"已被第 14 节第 32 条取代 |
| 版本号 | 1.1.0(Minor) |

**落地现状(2026-10-15)**:逐阶段的完成情况与剩余项见第 13 节。一句话概括:**本机文件**来源(四种格式)
已真机跑通;**HTTP 下载**来源代码完成,真机验收只差"真下载"那三项(受这张网络的客户端隔离限制,不是
代码问题);**HTTP 上传**来源(服务端 + 网页)与 **§9.1 的空间门**尚未开工。本文其余部分写的是**设计与
决定**,不表示已经落地 —— 状态一律以第 13 节为准。

## 2. 总体结构:三层 + 三种来源

安装逻辑照参考实现 sphaira 的三层解耦(`src/sphaira/sphaira/`):

```text
容器层  container/nsp.cpp   PFS0(NSP / NSZ)
        container/xci.cpp   HFS0 + secure 分区(XCI / XCZ)
        (MSP 这种 mod 包不在范围内,理由见第 7 节)
来源层  source::Base(可随机读) / source::Stream(只能向前读)
流水线  ui/menus/install_stream_menu_base.cpp 的生产者-消费者环形缓冲
        (mutex + condvar,安装器按 ReadChunk 消费)
```

三种来源都按**偏移取数据**(HTTP 客户端用 Range;浏览器上传由服务端指定区间;本地文件直接 seek),
共用同一条安装流水线:

**环形缓冲取 8 MB**(参考实现是 1 MB,那是给它自己"从头顺流"的用法定的):我们的生产者是**按区间
取数**的(第 3 节),一次请求最大就是 4 MB 的块,缓冲必须容得下"一次请求 + 安装器正在消费的那一段",
所以 8 MB 是最小的合理值 —— 4 MB 放不下 4 MB 的块加消费者手里那部分。安装器的读窗口取 1 MB。

**NSZ / XCZ 需要 zstd,而它已经在依赖里**:参考实现是从 GitHub 拉 zstd 源码编译(`FetchContent`,
链 `libzstd_static`);我们不必拉源码 —— 固定的 devkitPro 镜像里已经有
`portlibs/switch/lib/libzstd.a` 与 `zstd.h`(实测),Makefile 的 `LIBS` 加一个 `-lzstd` 就行。
NSZ/XCZ 的分块解压格式照参考实现的 `yati/nx/ncz.*` 搬(同一个 GPLv3,可以照搬逻辑)。

| 来源 | 传输 | 续传 | 备注 |
|---|---|---|---|
| 本机 SD 文件 | 直接读文件(随机读) | 天然可续传 | 卡上有没有那个文件由用户决定;能不能装得下不是这条来源的问题(见下) |
| HTTP 下载(主机作 client) | libcurl 按区间取数 → 环形缓冲 | HTTP Range 续传 | 需要 URL 输入入口(手机网页上粘贴为主,主机系统键盘为备用) |
| HTTP 上传(主机作 server) | 浏览器按服务端指定的区间分块 POST → 环形缓冲 | 按各内容的已收字节续传 | 页面同时提供"提交 URL"输入框,等价地发起上一种来源 |

## 3. HTTP 服务端实现方式(结论;**M4,尚未开工**)

**实现方式按平台实测决定。**

| 部分 | 选择 | 说明 |
|---|---|---|
| HTTP 报文解析 | **picohttpparser**(MIT:96 行头 + 715 行 C) | 只依赖 `<stdint.h>` / `<sys/types.h>`,在 devkitA64 上开箱即编;被 h2o 等成熟项目长期使用 |
| 服务端(accept / 读 / 写 / 路由 / 生命周期) | **我们自写薄层**(约 300–400 行) | 架构照工作区里的 `src/sys-agent/third_party/ftpsrv`(MIT):**单线程 + poll/select、定长缓冲、无动态分配**;它已被移植到 Switch(应用模式与 sysmodule 模式都在用 —— 我们自己的 FTP 就是它) |
| 客户端(下载) | **libcurl**(依赖里已有) | 与上面的服务端互不相干;不引入第二套客户端 |

**上传协议:分块 POST + 显式偏移,不用 WebSocket**。理由:

- 浏览器能**原生流式**发送 `File`(XHR/fetch 直接把 File 当 body),逐块 POST 让每一块成为独立请求:
  断线可续、失败可重试、服务端不需要维护长连接状态;
- WebSocket **不能直接把 File 流式发出去**:必须在 JS 里切片再用 `ws.send()` —— 等于做同样的事,
  还要多一层协议与连接管理,而且 WS 没有"续传"语义;
- 方向性需求是"上传 + 状态回报":状态用 `GET /status.json` 轮询最简单可靠(SSE/WS 都属过度设计)。

页面上传流程(纯 HTML + 原生 JS, 电脑/手机自带浏览器直接可用):

```text
选文件 → 页面问 /status.json:"下一个要哪个区间" → 服务端回 <offset, size>(或"已取齐")
  反复 POST /upload?offset=<n> (body = file.slice(n, n+size);size 由服务端决定,固定 4 MB)
  XHR 的 upload.onprogress 显示进度 → 每块成功后服务端回新的"下一个区间"
区间取完 → 服务端做收尾(进入安装阶段) → 页面轮询状态直到出结果
```

**块大小 4 MB、同一时刻只传一个块(不做并行分块)**:服务端是单线程的,收一个块的过程中没法同时
应答别的连接,所以块越大,观察者页面的进度就越"一顿一顿";4 MB 在局域网上约一秒,进度看着是连续的,
而每块的固定开销(一个请求头 + 一次写盘调度)仍然可以忽略。并行分块会带来"多个块同时落在同一个
占位里"的写入竞争,收益(局域网本来就跑不满)远小于复杂度,因此不做。

**页面提交 URL 的交接**:用户在页面上填了下载地址并按下按钮后,请求打到 `POST /url`(而不是
`POST /upload`),主机**不下载任何字节**,只做三件事:校验(`http` / `https`、长度上限,
不做别解析)、把它存进任务的 `install-task.json`、返回一个 **task id**。之后这条任务就是
**下载来源**(与主机侧"下载安装"完全同一条路:第 9 节先做 Range 探测,再取头部与 CNMT),
`source` 字段从 `http-server` 变成 `http-client`,状态机、进度、取消、续传全部沿用同一套。
于是"上传"和"下载"**不会同时活着**:一个任务同一时刻只有一个来源。

**服务端在任务进行中继续 `listen`**,不要提交完就关 —— 页面正是靠 `/status.json` 显示进度的;
关掉监听等于把手机页面踢下线(它会显示"主机已离线")。占用极小:一个 listen socket,加上
每次轮询几十微秒。销毁时机只有两个:**出结果页**、或者**用户退出安装页**(按 `B` 确认后)。

**取数顺序由服务端决定,不是"从头顺流"**:服务端**先只取容器头部与 CNMT**(小范围),据此得到版本、
类型与内容表(含"是否要跳过"),再逐个内容取数据(每个内容一条自己的偏移链)。对本地文件是 seek、
对 HTTP 是 Range 请求、对浏览器上传是"告诉页面下一个要哪个区间" —— 三者共用同一套逻辑。

### 3.1 怎么引入(vendored picohttpparser + 我们的薄层)

- **vendored 形态**:只取两个文件、**钉一个 commit**(不要跟 `master`):
  `source/third_party/picohttpparser/{picohttpparser.h, picohttpparser.c}` + 同目录 `README.md`
  (记录来源 URL、commit hash、两个文件的 sha256、许可证(MIT 或 Perl 二选一,我们按 MIT)、取用日期、
  升级步骤)。不克隆仓库、不加子模块;两个文件合计约 810 行,人工审阅成本很低。
- **薄层**(`source/net/http_server.*`):
  - 单线程 poll/select 循环(照 ftpsrv 的 `platform/nx` 经验:优先 poll,不可用则 select),
    服务端线程用 libnx `threadCreate` 创建、**栈页对齐**(本仓库踩过的坑);
  - 五个端点:`GET /`(自包含页面)、`GET /status.json`(只读状态)、
    `POST /url`(页面上粘贴的下载地址:`url=<percent-encoded>`)、
    `POST /upload?task=<id>&offset=<n>`(请求体**流式**读,直接喂环形缓冲)、
    `POST /cancel?task=<id>`(页面上的取消,二次确认在页面里做);
  - **页面不自己记状态**:打开时先读一次 `/status.json`,由主机告诉它现在是哪一屏
    (等待来源 / 只读观察 / 传输中 / 已结束),然后按状态渲染。刷新页面、换设备、断线重连
    因此都是同一套逻辑,不需要页面自己存任何东西;
  - **页面文本靠注入,不写死在 HTML 里**:HTML 里只留一个标记行(例如
    `<script>window.__STR__=/*PAGE_STRINGS*/null;</script>`),服务端返回页面时把它换成
    一份**页面专用的两列表**(`source/i18n/`,与 App 的 UI 文案同一套检查),
    其余文字一律由 JS 填 `textContent`。这样"页面文案进 i18n 表"这条不是口头约定,
    而是有唯一落点、也能被 `tools/check-i18n.py` 覆盖;
  - **连接要有超时**:手机被关机/走出热点范围时 TCP 不一定马上报错,读超时(15 s)后把这条连接
    判死并把任务转"已中断",不能挂着线程等对方;
  - **第一块要带文件身份**:页面在发第一块时带上 `name=<文件名>&size=<字节数>`,服务端据此记下
    `containerSize` 与文件名(进度页要显示它、续传要用它三重确认来源同一个文件);后续块只带
    `task` 与 `offset`;
  - 只支持我们页面用到的报文形态:页面用 XHR/fetch 裸 body(无 multipart)、响应不压缩、无 TLS;
  - 请求体同时支持 `Content-Length` 与 `Transfer-Encoding: chunked`(各十几行);
    **头部总量设上限**(例如 8 KB),畸形请求不会把内存顶爆;
  - 出错一律返回明确的 HTTP 状态码 + 一行 JSON,便于页面直接显示原因。
- **任务互斥(多标签页 / 多设备)**:真正的"活动"是主机侧**唯一的任务对象**,不是某个浏览器标签页。
  - 任务创建时生成 **task id**;推进类请求必须带着它(`POST /upload?task=<id>&offset=<n>`),
    主机校验"是当前任务"且"`offset` 正好等于期望的下一个字节",否则回 **409 Conflict** +
    当前状态 JSON(含真实 offset);带**旧 task id** 的请求永远碰不到新任务;
  - `GET /status.json` **永远只读**:state、task id、来源、按体积的进度、当前文件名、期望 offset、
    剩余字节/ETA、最后的错误 —— 任何标签页都能看并渲染进度,但**只有持有当前 task id 的页面能推进它**;
  - 于是:第二个标签页是**只读观察者**(入口禁用,写明"已有安装在进行中");上传中刷新页面会从
    `/status.json` 拿回 task id 与 offset **断点续传**(既不重传,也不会产生第二个任务);
    重复/乱序的分块被 offset 校验天然挡掉,页面照服务端回报的真实 offset 重新同步即可;
  - **观察者页面可以"取消",但必须二次确认**(写明会丢弃本次已接收的进度)。服务端不认来源 ——
    "内网、不做认证"是既定取舍(第 8 节)。
- **端口策略**:默认用**固定端口 1234**;若已被占用,则退让 —— 改用内核分配(`bind(0)`),
  再用 `getsockname` 读回**实际端口**。屏幕上的地址文字与二维码**永远用实际端口**(见第 8 节),
  用户不需要记端口。
- **构建集成**:两个库文件放在 `source/` 下(`INCLUDES := source` 已覆盖),`picohttpparser.c` 作为一个
  独立编译单元加进 Makefile 的 `SOURCES`。若 vendored 文件触发告警,**在 Makefile 里给它单独一条规则**
  (放宽告警级别)而不是去改它的源码 —— 我们自己的代码继续维持零告警。
- **HTTPS 的边界**:我们自己的服务器**不需要 TLS** —— 局域网页面走 `http://<ip>:<port>`
  (也正因为不是安全上下文,`navigator.wakeLock` 用不了,见第 8 节);而"用户提供的下载地址"里的
  `https://` 仍要能下:那条路走 **libcurl**(依赖里已有,配 mbedTLS,按本项目既有决定关闭证书校验,
  用户不需要放 CA 文件)。只保留 libcurl 这一套客户端。
- **登记与自检**:按仓库规矩,同一次改动里在 `AGENTS.md` 的目录规划登记这份 vendored 库(用途 + 来源);
  在 `tools/verify-release.py` 里核对 `picohttpparser.h` / `picohttpparser.c` 的 sha256,
  防止第三方代码被悄悄改动。
- **测试分工**:薄层里能脱离 socket 的部分(请求行/头解析的封装、offset 与长度校验、状态 JSON、
  进度换算)进主机测试;真机只验证"4.65 GB 上传 + 断线续传 + 长时间不睡",
  即第 12.2 节的 T7、T8、T18 —— 其中"乱序/重复块"由 offset 校验挡掉,属于主机可测的判定逻辑,
  真机只确认一次"重复块不会把占位写坏"。

## 4. 端到端流程(三种来源共用)

```text
① 选来源:SD 文件 / 提交 URL / 浏览器上传(上传要先有网络:热点或与手机/电脑同一个 Wi-Fi;
  主机自己没连上网络时,这一屏不显示地址与二维码,只提示先去系统设置连网 —— 见第 9 节)
② 容器识别(magic 优先、扩展名为辅):PFS0(NSP/NSZ)/ HFS0(XCI/XCZ);不支持的容器(如 `.msp`)在这里直接拒绝(第 7 节)
③ **只取头部与 CNMT**(小范围):得到版本、类型与内容表(meta 内容的 NCA 头用 spl 的 header key 解,载荷是明文)。
  走"下载地址"这条来源时,在这之前先做一次 **Range 探测**(拿不到 `206` + `Content-Range` 就直接拒绝)
④ **跳过判定**(第 9 节):已装同版本 → 「已安装,跳过」;机器上已有更高版本且默认不允许降级 →
   「已有更高版本,已跳过」。两种情况**都不启动传输**,直接进结果页
   (参考实现是在"传完必要内容"之后才判定;我们提前到取 CNMT 之后,省掉一次几个 GB 的无效传输 —— 这是有意偏离参考实现之处)
⑤ 确认页:显示"这是什么"(游戏名 / 版本 / 类型: 本体·更新·DLC)/ 总大小 / 目标存储
   —— 机器上根本没装这个游戏时,额外提示"安装后即可使用 agent"(前提是版本受支持)
⑥ 前置检查(第 9 节):keygen / 目标存储 / 剩余空间 / 可建占位 / 票据 / **目标游戏未在运行**
⑦ 在目标存储建占位(用 ③ 得到的内容表;不落盘临时文件,边收边写)
⑧ 逐内容取数据 → 写入占位;票据/证书收进内存
   (占位大小来自内容表,不需要先算哈希;默认不校验内容,见第 5 节)
⑨ **全部内容取齐后才逐个 `Register`**(含 meta 内容)—— 在写库之前的任何失败都不会留下"已注册但无条目"的半成品;再写元数据库条目(用 ③ 拿到的 CNMT,不重复读)
⑩ 导入票据(es::ImportTicket,机器上已有则跳过)→ **删除同 title 的旧版本**(见下)→ 写元数据库
   → PushApplicationRecord(记录写在**本体 id** 下,记录里放本次的 meta 键;+ HOS ≥ 6 的 avmPushLaunchVersion)
⑪ 重新 Collect():首页反映新状态(版本变 supported → 可安装 agent;或"已安装"等既有状态)
```

**⑫ 跟着把 agent 装上**(第 14 节第 32 条):这一步不属于引擎,而是这次运行的第二半 —— 结果页
起来之前,若⑪算出的计划说"该装/该修",就用与首页按钮完全相同的那条路径(同一份清单、同一个
payload 来源、同一个引擎)把 agent 写进去;计划说"已是最新"就什么都不写;计划被门控挡住就把
原因写进 `log.txt` 并在结果页给一句能照做的提示。进度卡换成"正在安装 agent",数字跟着它自己的
文件走(3 个文件,没有字节数),所以那一屏不会显示 `0.00 / 0.00 GB`。

**⑨ 之后进入"收尾",收尾一旦开始就不再接受取消**:删旧版本与写元数据库是一组原子动作,中间被打断
会留下"内容在、条目不在"或反过来的状态;因此从第一个 `Register` 起,取消入口关闭,屏幕上显示
"正在收尾(不能取消)",直到出结果页。

**元数据库条目(记录)必须按系统的形状写**:记录 = 8 字节 `ContentMetaHeader`(**不是** CNMT 文件
开头那 8 字节的 title id)+ 扩展头 + 每个内容一条 24 字节 `NcmContentInfo`(CNMT 文件里每条内容前面
那 32 字节 SHA-256 **不属于**记录)+ 内容元信息表;**包自己的 meta 内容(.cnmt.nca)排在第一条**
(CNMT 的内容表里没有它,要补上),且内容的 `content_type` 用 `NcmContentType` 值(0 Meta / 1 Program /
2 Data / 3 Control / 4 HtmlDocument / 5 LegalInformation / 6 DeltaFragment)。
把 CNMT 文件的字节直接当记录写进去,系统会**收下但读不出来**:`ncmContentMetaDatabaseListContentInfo`
返回一堆全 0 条目、`nsGetApplicationControlData` 报 `0x8C10`、首页把已安装的游戏画成空白格 —— 真机实测过
整条链路(对照证据:系统自己写的基础本体记录长这样:8 字节头 + 16 字节扩展头 + 4 条 24 字节内容信息,
第一条就是 meta 内容)。记录由 `BuildMetaRecordBlob()` 生成,主机侧有逐字节的用例钉住布局。

**记录里的内容表只列"这次真的装上了的内容"** —— 具体说:**delta 片段不列**。CNMT 会列出 delta
片段(它是"相对某个已有内容的变化量"),但包里**根本不带**这些文件,我们也不会去取,所以记录里也不
该有它们:记录就是"这个版本由哪些内容组成"的答案,里面每一条都必须在存储里找得到。参考实现做的就是
这件事(`yati.cpp`:解析 CNMT 时 `if (info.content_type == NcmContentType_DeltaFragment) continue;`,
然后 `content_count = infos.size() + 1`),而且它对剩下每条都要求"包里真有这个 NCA"。
真机踩过的坑:我们原先把 CNMT 的内容表原样抄进记录,于是记录声称 33 条内容、实际只有 3 条——以前
delta 恰好还在卡上(早先别的工具装过同版本)所以看不出来;用户用 DBI 把所有非本体包删干净之后再装
v2.0.0,系统就判定"内容缺失"、**拒绝启动游戏**,DBI 删除时也把这些条目标成一长串"缺失"。

**判"这条记录可用"时还要逐内容确认它在存储里**(`ContentInstaller::RecordIsUsable()` 里的
`ncmContentStorageHas`)。只查"列表读得出来"不够:"记录在、内容不在"正是上面那种坏状态,而把这种
状态判成"已安装"会让程序永远拒绝修复它。逐内容查过之后,再装一次就会把它修好——已经在存储里的内容
会被跳过,所以修复很便宜(不搬字节)。

**meta 内容(.cnmt.nca)必须由我们自己注册**:它是唯一不在任务清单里的内容(CNMT 不列自己),而读
CNMT 的那一步只往**占位**里写、挂载占位去读;如果就停在这儿,记录里会写着一个存储里根本不存在的内容
——系统因此拒绝启动游戏。参考实现在注册阶段就把它一起注册(`RegisterNcasAndPushRecord` 第一件就是
注册那个 CNMT NCA),我们是后补的:`ContentInstaller::Register()` 现在显式接收它、并排在第一条。
真机踩过:先前之所以时好时坏,是因为"占位挂载失败→先注册再挂载"的兜底路径**顺手**注册了它;哪条路径
被走到决定了装完能不能启动。

**Update / DLC 的"应用记录"挂在什么 id 下**决定了首页能不能画出这个游戏:记录要写在**应用 id**
(本体 id,= patch id ^ 0x800)下,记录里放本次的 meta 键;写在 patch id 下会让系统多出一个"什么都没有"
的应用格(真机实测)。反过来说,如果**旧版本的本程序**已经留下过这样一格,安装时的补救是:在写本次记录
**之前**清掉"本次 meta id"这一行的记录表(`ns` 的 `DeleteApplicationRecord`;**顺序不能反**,这个调用同时
等于"清空该应用的记录表",写在 push 之后会把刚写好的记录抹掉 —— 真机实测:游戏会从首页消失,直到下次安装
把记录写回去)。该调用不删内容。

**"已装"还要求"机器真的能用"**:跳过判定除了"这台机器上有这个版本"还要问一句"系统读得出这条记录吗"
——记录挂在正确的应用 id 下、且 `ncmContentMetaDatabaseListContentInfo` 能读出**带 Control 内容**的
非空内容表(只有"读得出来",首页才有图标与版本号可显示)。两者有一条不满足就照常走收尾:内容都已在存储里,
不搬字节,只把记录与记录表修好。这样"旧版本程序留下的坏状态"不必卸载就能自愈。
`Finish()` 每次都会把这条读回结果写进日志,以后"首页为什么是空白格"不必靠猜。

装完立刻重新 Collect() 时,`nsGetApplicationControlData` 可能还没重建好缓存而短暂失败(真机实测:
安装返回后立刻读是 `0x8C10`,过一会儿再读正常),因此该调用带**3 次、每次间隔 150 ms** 的重试。

**收尾必须删掉同 title 的旧版本**:参考实现在安装 Patch 时,会遍历**所有存储**,列出同 title、
同类型(Patch)的元数据条目,把"除了本次安装的那一个之外"的旧条目连同其内容一起删掉 —— 否则装上
3.0.3 之后 2.0.0 仍会占着几个 GB(用户实测:装完 3.0.3,机器上只剩 3.0.3)。执行顺序照参考实现:
装内容 → 导票据 → **删旧版本** → 写库并推记录。
**这一步最容易踩的坑**:删旧版本时要**跳过本次安装复用/跳过的内容**(参考实现用 `it->skipped` /
`cnmt.skipped` 判定),否则会把刚注册好的共享内容删掉。

**注意**:通用安装器不再有"版本必须先低于目标"的前置限制 —— 用户可以装任何版本、任何容器的内容,
只要第 9 节的检查过得了。

## 5. 校验与安装选项(默认值跟随参考实现)

参考实现在 `include/app.hpp` 里给出的安装选项默认值(括号内是它的 UI 标签),我们**逐项跟随**:

| 选项 | 默认 | 含义 | 我们 |
|---|---|---|---|
| `install_sd` | **true** | 装到 SD | ✓(与既有决定一致;SD 空间不足时询问装机身) |
| `install_sysmmc` / `install_emummc` | false | 装到机身 / emuMMC | ✓(默认关,只作"空间不足时"的备选) |
| `skip_if_already_installed` | true | 已装则跳过 | ✓ |
| `allow_downgrade` | false | 允许降级 | ✓ |
| `skip_base` / `skip_patch` / `skip_addon` / `skip_data_patch` / `skip_ticket` | false | 跳过某类内容 | ✓(默认全关 = 全部安装) |
| `skip_nca_hash_verify` | **true** | **跳过** NCA 全文件 sha256 校验 | ✓ |
| `skip_rsa_header_fixed_key_verify` | **true** | **跳过** NCA 头 RSA 固定密钥验签(该验签用于识别 NSP/XCI convert) | ✓ |
| `skip_rsa_npdm_fixed_key_verify` | true | 跳过 NPDM 验签(参考实现里是未被实现的桩) | ✓ |
| `ignore_distribution_bit` | false | **不忽略** distribution bit → 即会把它从 GameCard 改成 System(卡带内容才能在 SD/机身启动) | ✓(XCI 必需) |
| `convert_to_common_ticket` | **true** | 把个性化票据转成 common 票据( **[需要 keys]** ) | **值跟随,行为不做**:官方公共票这一步本来就是空操作(随包证书链验签通过即不改);个人票才需要本机 `setcal` 设备密钥 + `prod.keys` 里的 `eticket_rsa_kek`。我们原样导入票,交给 `es` 判断(第 6、9 节,第 14 节第 36 条) |
| `convert_to_standard_crypto` | false | 转成 ticketless 标准 crypto( **[需要 keys]** ) | **未实现**(默认关;实现它要拿 `titlekek` / `key_area_key` 写进 NCA 头的 key area,即必须读 `prod.keys`) |
| `lower_master_key` | false | 用 master key 0 加密 key area( **[需要 keys]** ) | **未实现**(默认关;与上一项同源,同样必须读 `prod.keys`) |
| `lower_system_version` | **true** | 降低 CNMT 里记录的系统版本要求 | ✓ |
| `ticket_only` | false | 只导票据不装内容 | ✓ |

**这套默认的两个直接后果**:

1. **第三方改造内容可以装**(重打包 NSP、NSP↔XCI convert 都行)——因为两项校验默认就是跳过的。
   但"能装"不等于"能运行":运行取决于用户自己的系统(Atmosphere/sigpatches 是否允许未签名内容)。
   我们自己主动做的改造(XCI 的 distribution bit、`lower_system_version`)按参考实现的方式内部标记,
   **结果页不为"跳过了校验"加任何额外提示**(与参考实现一致,不多做一步)。
2. 默认里有三项标着 **[需要 keys]**,它们的**默认值我们照抄,转换本身 1.1.0 不做**(见上表):
   - `convert_to_common_ticket`(默认**开**):对官方包是空操作(公共票验签通过就不改),对个人票才
     要用 `setcal` 的设备密钥重写票据;而设备密钥本身被 `eticket_rsa_kek`(`prod.keys`)加密。
     我们**原样导入**票:官方包与参考实现结果一致;个人票若是为本机签发,交给 `es` 通常照用,若是别的主机
     签发的,则任何工具都救不了(转换用的也是**本机**设备密钥,device id 不匹配同样失败)。
   - `convert_to_standard_crypto` / `lower_master_key`(默认**关**):把标题密钥写进 NCA 头的 key area,
     真需要 `prod.keys`;默认关,所以正牌任天堂内容(自带公共票)**完全不需要任何 keys**。
   结论:**本 App 的安装路径不读 `/switch/prod.keys`**(选项结构里保留 `MayNeedKeys()` 这类判据备用,
   但它不影响当前行为)。哪天真要做这两项转换,那时的规矩是"缺 keys 就明确报错,绝不静默跳过"。

**不提供更改界面(1.1.0 的决定)**:上面这些选项在 1.1.0 里是**固定值** —— 安装页不给开关,
**详情页也不列出**。理由来自一次成本评估:值得暴露的其实都是高风险开关(部分安装 / 仅安装票据 /
emuMMC / 需要 `prod.keys` 的转换项,其中几项在我们的流程里没有意义,另几项会把机器留在半装状态),
而"跳过校验"一旦做成显眼开关,等于鼓励用户放宽校验;真要提供界面,成本主要在**列表控件**
(我们现有 UI 里没有任何列表控件)+ **每项两列文案** + 后果提示 —— 照参考实现搬 19 项约 2–3 天,
只暴露 5–7 项约 1–1.5 天。
但实现上仍会把它们做成**一个带默认值的选项结构**(而不是散落各处的常量),将来要加界面时只需补
"列表 + 文案"两块,不必返工引擎。

## 6. 密钥:安装路径完全不读 `prod.keys` / `title.keys`

**1.1.0 的安装路径不用任何密钥文件**,四种格式、三种来源都一样:

- 解 NCA 头的 header key 由主机 `spl` 现算(`splCryptoGenerateAesKek(HEADER_KEK_SRC, …)`);
- **CNMT 走"装进占位再挂载"这条路**:meta 内容写进占位 → 用 `ncm` 给的占位路径挂载为
  content-meta 文件系统 → 读出 CNMT。这条是参考实现的序列,也是**唯一**不需要我们解密任何东西的路:
  标题密钥加密的 meta 内容(官方更新包就是这样)由系统自己的文件层解开,所以票与密钥文件都不参与
  "能不能读出 CNMT"这件事;
- 哈希校验与 RSA fixed-key 验签都**默认跳过**,而本 App 这两条检查根本没有实现——行为上等价于参考
  实现的默认值(它实现了但默认不查);改了 distribution 位的头带着过期签名照写,靠的也是这条默认;
- 票据**原样导入**:公共票(官方渠道的包,占绝大多数)本来就与密钥文件无关;个人票交 `es` 判断
  (为本机签发的通常照用)。参考实现那套"转公共票"我们不做,它在官方包上本来就是空操作——
  细节与"它到底需不需要 keys"见第 5 节与第 14 节第 36 条。

**第 5 节里标着 [需要 keys] 的两项转换(`convert_to_standard_crypto` / `lower_master_key`)1.1.0
未实现**,默认又是关的,所以它们不会把密钥文件变成前置条件;哪天真要做,届时的规矩是"缺
`/switch/prod.keys` 就**明确报错**,绝不静默跳过转换"。`MayNeedKeys()` / `needs_keys` 这套判据留在
选项结构里备用,当前不影响任何行为。

## 7. 不支持的容器:MSP(明确不做)

**MSP 不是任天堂格式**,而是参考实现自定义的 **mod 包**格式:装 MSP 就是往 SD 上写文件,
包里的 `romfs` / `exefs` 条目落到 `/atmosphere/contents/<title id>/…`,IPS 补丁落到
`/atmosphere/exefs_patches/<title id>/…`。它不是"安装一个游戏或更新",而是**铺 mod 文件**。

**1.1.0 不实现**,理由是它与本应用自己的产品正面冲突:agent 装的正是
`/atmosphere/contents/01006F8002326000/exefs/{subsdk9, main.npdm, acnh-agent.version}`,
而同一个 exefs 目录里每个文件名只能有一份 —— 一个带同名文件的 ACNH mod 包和 agent 会互相覆盖
(后装者胜),轻则聊天码功能失效、mod 失效,重则留下"两者混搭"的文件组合让游戏起不来。

**影响与替代**:`.msp` 文件在容器识别阶段直接被拒("不认识这个文件"),结果页的提示里建议用户
用支持 MSP 的工具(例如参考实现 sphaira)安装这类 mod;如果将来要做,必须先定"与 agent 同目录时
怎么办"的策略(拒绝 / 备份后覆盖 / 直接覆盖),那属于新功能,不在 1.1.0。

## 8. 界面与文案

**入口**:

- 页眉**常驻「游戏安装/更新」**(英文 `Game Install / Update`;键位 **`＋`**),任何页面都能进;
  页眉从左到右读作 `＋ 游戏安装/更新 / Ⓛ 状态 / 详情 / 功能说明 Ⓡ` —— **不受 L/R 控制的那个
  入口单独排在最前**,受控制的三个页面挨在一起,而 `Ⓛ` / `Ⓡ` 分别贴在这一组的**两端**(打开它的
  键在左、关闭它的键在右),一眼就能看出哪几个是一组、以及是哪两个键在它们之间移动。页眉上写着
  的是**这个键会做什么**,不是"这一格配哪个键"。具体来说**页面分成两类**:
  - **`L` / `R` 在"给人看"的页面之间循环**(状态 → 详情 → 功能说明,两头都环绕)。这才是页眉上
    `Ⓛ` / `Ⓡ` 的含义:肩键翻页,以后再加同类页面**不需要新键**,手指也不用离开肩键;环中间那一页
    (详情)**不戴徽标**——没有哪个键直达它,画上徽标就是许一个没有键兑现的承诺;
  - **`＋` 是模式**(安装页排他、`B` 才能出),所以它保留自己的键、**不进环**;`－` 仍可直达功能说明
    (环上最后一站,留着是为了习惯),但页眉只写环的 `Ⓡ`,不给同一页画两个键;
  - 触摸仍然直达:页眉每一格都能点,点的行为就是"去那一页"(不经过环)。
  - **页脚补一句白话**:状态栏里除了 `Ⓑ 退出/返回` 还会写 `L / R 切换页面`(纯提示文字,不是
    控件 —— 它指向两个键,点它没有单一动作可做)。安装页(页眉标签页已隐藏、`L`/`R` 已失效)与
    进度页(整页没有外壳)不写这句。
  标签用名词、首页那个按钮用动作,风格与既有原则一致;
- 首页另给一个上下文快捷入口:`Unsupported`(版本不在支持范围)态主按钮
  **「安装游戏更新」**、副标题 **「升级完会自动安装 agent」**;**该按钮在这一态始终显示**,
  不再按"有没有更高版本"显隐(通用安装器不必替用户判断——他手上可能是别区版本、别的封装,
  或根本想装别的东西);
- `GameMissing`(机器上没有这个游戏)态:状态行下方补一句提示,说明**可以用本应用的安装功能
  装一份游戏本体**;其余六态不变。
  (顺带:这个按钮的旧副标题"原因写在详情里"在本态不再出现,实现时把这条 i18n 与其引用一并删掉,
  免得留下死字符串 —— `tools/check-i18n.py` 只查两列齐全,查不出没人用的条目。)

**安装页 = 全 App 唯一的模态页**——进入方式:页眉「游戏安装/更新」或上面的首页快捷按钮
(页面标题也用「游戏安装/更新」这个名字)。进入后:

- **页眉的四个标签页隐藏**(不是变灰):这一页是**排他的**,只能按 `B` 退出之后才回到其它功能;
  隐藏后腾出的位置显示**两条存储余量** —— `microSD` 与 `系统`,每条 = 标签 + **可用 / 总**
  (例如 `microSD 85.6 / 119.2 GB`)+ 一条按"已用 / 总量"画的条形。取数走
  `fsOpenContentStorageFileSystem(FsContentStorageId_SdCard / _User)` + `fsFsGetFreeSpace` /
  `fsFsGetTotalSpace`(与第 9 节的前置检查**同一来源**),在绘制里**每秒刷新**一次;进入安装页先读
  一次,安装前再读一次作为判据。读不到时按参考实现的做法**不隐藏**,但显示 `--.--` 而不是
  `0.0 GB`(参考实现那个 0.0 GB 是它预置 `1/1` 防除零的副产物,不是有意的文案)。存储条是**指示器**,
  不进动作表。
- **`B` 的语义**:没有任务、服务端也没在监听 → **直接回到进入前的页面**;服务端在监听或任务
  进行中 → **二次确认**(确认后销毁服务端、中断传输;已收数据保留,下次可续传)。

**页面按"先选来源、再走各自的流程"分四步**(三条来源共用后半段):

1. **选来源**:一行支持格式提示(`支持 nsp / nsz / xci / xcz`)+ 三张卡片 ——
   `Y 本机文件`(从 SD 卡选一个文件安装)、`X 下载安装`(**填写网址,下载安装**)、
   `A 上传安装`(通过手机/电脑浏览器上传安装)。这一屏**只显示三个入口**;存储余量在页眉里;
   "未完成的安装"只有当它真的存在时才会多出一条提示条(带【继续】【放弃(清理)】,语义见第 10 节)。
   **三张卡片同时是可点的**(触摸和按键等价,和首页那几张卡片一致);确认页、进度页、结果页
   不设可点控件 —— 那几屏是"看进度"的地方,只认按键(见第 14 节第 16 条)。
2. **各自的入口动作**:
   - **本机文件** → SD 文件列表(需要**新的列表控件**:列表 + 焦点 + 滚动 + `Y 上一级` +
     `A 选择`;只列支持的扩展名,其余置灰)。**每行右侧写"这是什么 + 多大"**
     (`安装包 · 4.3 GB` / `忽略 · 1.2 MB`;目录写 `目录`,不写大小):同一款游戏的两个更新包
     差别主要就在这个数字上,而文件名本身答不了"这是不是我想要的那个包"。大小用与确认页
     "大小"一行相同的二进制单位(`util/size_text.hpp`,主机测试钉住单位边界),两页不会对同一个
     文件给出两个数;名字过长时按右侧信息截断(带省略号),不会互相压字;
   - **下载安装** → **地址屏**。2026-10-15 定稿的版式(稿子见 `~/.codex/visualizations/` 下
     `m3-download-*` 那一组)**把"两条给地址的路"放在一屏里**:
     - 上面一张**整块可点**的卡:`Ⓐ 输入网址` + 小字 `用系统软键盘输入下载网址`;软键盘初始文本
       `http://`(libnx `swkbd`;工作区参考实现里同样是这一用途:`ui/menus/ghdl.cpp` 的
       `PromptDirectLink()`)。输过一次之后卡里多一行 `上次:<地址>` —— 改一个字符重试不必重敲;
     - 下面一块是**第二条路**,也是这条来源的**主入口**:标题 `用手机或电脑的浏览器打开下面的地址`
       + 大字的 `http://<ip>:1234` + 二维码(`扫码打开`)+ 一句
       `在网页里粘贴下载网址 —— 不用一个字一个字地敲` + 状态行 `● 正在等待连接……`。
       手机页提交地址走 `POST /url`(第 14 节第 28 条,主机把任务从 `http-server` 切成
       `http-client`)。**这一块随 M4 的服务端一起出现**:服务端落地之前这一屏只有上面那张卡,
       版式不变(留白在下半屏);
     - 页脚 `Ⓐ 输入网址` / `Ⓑ 返回`,严格照 `App::DrawFooterHintPair`:徽章在左、文字在右、
       两条从左往右排、右侧留给构建戳 —— **`Ⓑ` 不顶到右边**(这条是 2026-10-15 按实现校正的);
     - 底部一行小字:左 `地址要支持断点续传(HTTP Range),不支持会被拒绝`(规则**前置**,不等失败才说),
       右 `支持 nsp / nsz / xci / xcz`;失败时另加一条暖色条(原因 + 出问题的地址),此时不再重复通则;
     - **没连网时**整屏换成一张卡:`请先在系统设置中连接网络` +
       `连接到手机热点,或者与手机/电脑连接到同一个 Wi-Fi 下即可`,页脚 `Ⓐ 重新检测`
       (与上传来源同一套规矩:没网时两条路都不通,所以既不出地址也不出二维码)。进这一屏与按 `A`
       各查一次 `nifm` 的地址;
     - 措辞**一律不写"主机"**:这两个字在"Switch 主机 / 手机 / 电脑"之间指代不清,直接省略或说
       "本机"(定稿稿子逐张核对过);
     - 文案(中英两列):`填写网址,下载安装 —— 边下边装`、`输入网址`、`用系统软键盘输入下载网址`、
       `上次:%s`、`地址要支持断点续传(HTTP Range),不支持会被拒绝`、`请先在系统设置中连接网络`、
       `连接到手机热点,或者与手机/电脑连接到同一个 Wi-Fi 下即可`、`重新检测`;失败三条复用
       `连不上这个地址…` / `这个地址不支持断点续传…` / `地址打不开(HTTP %s)…`。
       (`连不上这个地址`这条由真机实验定名:主机**明明有网络**(日志里 `update check` 成功),
       只是连不上那个地址,写成"先在系统设置里连上网络"会把人带偏。)
   - **上传安装** → 显示地址(大字)+ 二维码 + "正在等待连接"状态,与下载屏下半屏**同一块版式**
     (只有标题与提示语不同:这里说"选择要安装的文件")。**HTTP 服务端就绪于这一步**:还没有任务时,
     只有停在这一屏(或下载屏)才 `listen`(离开就去挑文件了,不白占端口);**任务一旦开始,
     服务端活到出结果页或退出安装页为止**(页面靠它看进度,见第 3 节)。**没连网时不出版本与二维码**,
     只给"请先在系统设置中连接网络"那张卡与 `Ⓐ 重新检测`(第 9 节)。

   **两条来源共用同一块"来源屏"**(地址 + 二维码 + 等待连接):网页本身就同时提供"选择文件"与
   "粘贴下载网址"两个入口,所以主机这边只是**换了标题与提示语**。2026-10-15 起,下载屏**自己**
   也带这块(不再只靠"按 X 进来时提示去手机上粘"),两条来源因此长得一样、只是首屏的输入方式不同。
3. **确认页(共用)**:主机取到头部与 CNMT 之后显示"这是什么" ——(内容见下一段);
   页脚 `Ⓐ 开始安装` / `Ⓑ 返回`。**安装页里 `B` 的语义是"退一级"**:来源屏 → 离开安装页;
   文件列表 / URL 输入 / 上传等待 → 来源屏;确认页与结果页 → **回到本次是从哪一屏开始的**
   (本机文件就是文件列表,URL / 上传就是各自的输入屏),再按一次才回到来源屏。确认页与结果页
   都不是"退到来源屏"(那会一次跨两级,玩家挑错文件后想换一个就不顺手了);退一级时会把这个
   包连同它读 CNMT / NACP 时建的占位一起放掉(没装成的东西不该留在机器上),已经进到
   `Register` 之后的运行则什么都不回收 —— 内容和记录都是玩家的了。
4. **进度页(共用)**:**卡片第一行就是"这是什么"**(游戏名·版本·类型,与确认页同一句话)、
   右侧同一张封面;然后是阶段(接收 → 收尾 → 正在安装 agent)+「第 N / M 个内容」+
   **当前内容的文件名** + 条形进度与百分比 + 已传 / 剩余;`Y 取消`、`B 返回`
   (都要二次确认;进入"写库/删旧版本"的收尾阶段后两者都不再响应,屏幕上显示"正在收尾")。
   **进度页在传输期间不接受任何按键**(引擎占着这一条线程),页脚只写"传输进行中,请不要离开
   本页面";取消留到传输搬到工作线程之后再做。**"第 N / M 个内容"数的是正在写的那个**
   (`done_contents` 只数写完的,单内容包里整段显示"第 0 / 1 个内容",读起来像还没开始)。

**确认页**:显示解析结果 —— 游戏名 / 版本 / 类型(本体·更新·DLC)/ 大小 / 目标存储;
包里的版本受支持时,额外说明 **「装好后会自动安装 agent」**(第 14 节第 32 条:这一步真的会发生,
所以用"会"而不是"可以");版本不受支持时改说 agent 支持到哪个版本。不显示内部概念
(内容 id / sha256 / payload 等)。(会跳过的那两种情况在第 4 节 ④ 就处理掉了,不会走到这一页。)
**agent 的版本说明只对"管版本的那两种包"说**:本体与更新;追加内容(DLC)与数据补丁**不改游戏
版本**,所以确认页与结果页对它们**一个字都不提**(真机踩过:装一个 DLC 却弹出"agent 不支持此
版本" —— 那句话的前提是"这次安装会改变版本",而 DLC 不改变任何版本)。判定在
`install::MetaTypeCarriesGameVersion()`,主机测试钉住。
**卡片右侧放游戏封面,图从安装包自身取**:控制内容里每个语言一张图(`icon_AmericanEnglish.dat`、
`icon_SimplifiedChinese.dat`、…,与 NACP 那十六种语言同一套命名),按 **App 当前界面语言**挑
(与游戏名同一条规则,`install::ChooseIconFile()` / `source/install/icon_file.hpp`,主机测试钉住);
本语言的两张都不在时退到 `icon_AmericanEnglish.dat`,再退到"任意一张 `icon_*.dat`"(取名字最小的
那张,结果与目录列举顺序无关)。挑到的 JPEG 用 portlibs 的 libjpeg(`-ljpeg`)解一次、按盒子平均
缩到 200×200 画上去。**这样机器上没有这个游戏也照样有图** —— 从包里读,而不是问系统要:
系统那份控制数据只在游戏装着时才答(而且它答的可能是缓存里那份旧的,我们自己的收尾步骤会把它
清掉,真机上就出现过"封面自己消失")。包里没有控制内容、或控制内容里没有图时(小的追加内容就是
这样),才回头问系统 `nsGetApplicationControlData`(首页画图标用的同一个调用);两边都没有就
不画图,卡片照旧(封面只是"这是什么"的补充)。
**游戏名按 App 的语言取,主机系统语言的写法另起一行**:同一个标题在 NACP 里最多有 16 种语言的
写法,而 `nacpGetLanguageEntry()` 回答的是**主机系统语言**那一种 —— App 设成英文、主机是中文时,
确认页会显示中文游戏名,读起来像 App 忽略了语言设置(真机反馈)。所以:主行用 **App 当前界面语言**
(App 里玩家自己选的那个)的写法,主机给的名字**与它不同**时,在标题下面用小一号的灰字再给一行
(那正是桌面/相册里显示的名字,两个写法同时出现也正是"同一个游戏"的凭据);两边一样只留一行。
App 的语言在包里没有时才退回主机给的名字,再退到包里第一个非空写法。选择逻辑是纯函数
`install::ChooseTitleNames()`(`source/install/title_name.hpp`),主机测试钉住;屏上仍然只有名字,
内部 id 不上屏。
**"大小"取包自身的字节数**,不是"还要传多少":内容都已在机器上时后者是 0,屏幕上会变成
"0.0 GB",读起来像这个文件是空的(真机实测)。
**前置检查失败或需要询问时,停在同一张卡上**:标题就是原因,下面一行给"怎么办",
页脚 `Ⓐ 重试` / `Ⓑ 返回`(唯一的例外是"空间不足",那一屏是询问:`Ⓐ 装到机身` / `Ⓑ 取消`)。

**结果页**:**信息自带,不指望用户去详情页** —— 一屏里说清三件事:

- **这是什么**:游戏名 / 版本 / 类型(本体·更新·DLC),右侧同一张封面 —— 玩家在传输期间走开过,
  回来时要一眼认出这就是他刚才开始装的那个游戏;
- **做了什么**:成功 → 写入的内容数与总大小 + 目标存储;跳过 → **为什么跳过**;失败 → **一句话原因**;
- **现在怎样**:agent 的状态,取的是**这次运行的第二半**真的做了什么 ——「agent 已一并安装」
  (第 14 节第 32 条);已经是最新时是「agent 已经装好了」;那一半没能写成时是琥珀色的一句
  「agent 这次没能装上:回首页可以重新安装」(原因进 `log.txt` 与详情页)。只有第二半根本没被
  触发(比如这个包不改游戏版本)时,才回到旧的「可以安装 agent 了(首页按 A)」。

四种标题:**「安装完成」**、**「已安装,跳过」**(内容已装过,`skip_if_already_installed` 默认开)、
**「已有更高版本,已跳过」**(默认 `allow_downgrade=false` 不降级)、**「安装失败」**
(失败红、其余绿)。这两个跳过态的存在是必需的 —— 它们的传输**瞬间结束**,写不清用户会以为传输出错了。
"改造过的内容"(卡带镜像翻转 distribution 位)只在 `log.txt` 与详情页留痕,结果页不多说一句:
那句话玩家无法照做,而改造本身正是这次安装能成立的原因(用户 2026-10-15 提出删掉这行)。
**页脚只保留 `Ⓑ 返回`** —— 能在一屏里说清的事,就不把用户推去
别的页面。失败态同样只给**一行原因**;只有当原因本身放不进一屏(比如解析失败要写清是哪个容器、
哪一段偏移)时,才在那一行后面补一句"详见 `log.txt`"。详情页不为安装流程承担任何"补充说明"职责。
结果页**仍然在安装流程的模态里**(页眉继续隐藏标签页、显示存储余量;跳过时数字不变,一眼看出什么都没
写),按 `B` 才退出整个流程 —— HTTP 服务端其实早已在离开"上传安装"那一步时销毁(第 10 节)。

**页面文案与语言**:浏览器页面上的文字同样是用户可见文案 —— 页面文案也进 i18n 表(两列),由服务端在
返回 HTML 时按 App 当前界面语言注入;`/status.json` 里带机器可读的 `code` + 已本地化的 `message`,
页面优先显示 `message`,这样页面不必再维护一份错误文案表。

**浏览器页面(主机自己提供的那一页)**:整页是**一个自包含的 HTML 文件**(`data/installer_page.html.bin`,
CSS 与 JS 全部内联),**不引用任何外部资源** —— 主机常常只有手机热点、没有外网,任何 CDN 引用都会让
页面白屏。配色用 App 自己那套(奶油底 + 青绿),手机与电脑同一份内容、只是列宽不同。三屏:

1. **选择文件**(就绪态):`第 1 步 · 选择安装文件` 卡片(一个虚线框 + 「选择文件」按钮,电脑上可直接拖入;
   框下注明支持 `nsp / nsz / xci / xcz`)+ 一张"或者 · 粘贴下载网址(主机自己去下)"卡片(输入框 +
   「下载并安装」);底部三行说明:**保持本页在前台 / 本页不依赖互联网 / 主机屏幕上会同步显示同一份进度**。
2. **传输中**:文件名 + 大小、条形进度 + 百分比 +「已传 / 总量」+ 速度与剩余时间、
   「第 N / M 个内容」与当前内容文件名;一张独立的「取消本次安装」卡片(红字描边;**再点一次确认**),
   下方写明"取消会丢弃已接收的进度";再下面是"中断后重新打开本页、重选同一个文件即可续传"的提示。
3. **结果**:与主机结果页**同样的四态与三行信息**(这是什么 / 做了什么或为什么跳过 / 现在怎样),
   只有一个「关闭本页」按钮 —— 页面不重复主机那边的内部细节。

换一个文件、或主机把任务判成"不认识的文件",页面就回到第 1 屏并把原因写在卡片下方。
第二个标签页打开同一地址时,页面自动变成**只读观察者**(同样的进度,按钮换成
"已有安装在进行中" + 一个需要二次确认的「取消」)。

**二维码**:工作区现有的 `source/ui/guide_qr.cpp` 只负责把矩阵画出来,需要一个 **QR 编码器**;
用 Nayuki `qrcodegen` 的 **C 版**(MIT,与 GPLv3 兼容),vendored 在
`source/third_party/qrcodegen/`。选 C 版而不是 C++ 版的原因是本项目用 `-fno-exceptions`
编译,而 C++ 版会 `throw`;C 版不分配内存、不需要 C++ 运行时,由我们的薄封装
(`source/util/qr_code.*`)提供缓冲区并转成矩阵。出处、commit、sha256 记在
`source/third_party/README.md`,并由 `tools/verify-release.py` 每次核对。

**服务端生命周期**:没有任务时,只有停在"来源屏"才 `listen`,离开这一屏就销毁;**有任务时,
服务端一直活到出结果页或用户退出安装页** —— 手机页面靠 `/status.json` 看进度与取消,提前关掉
等于把它踢下线(第 3 节)。退出应用、其它页面都不监听。页面拿不到状态时显示"主机已离线(安装
可能已结束或你已退出安装页)",而不是一直转圈。内网行为,**不做认证**(屏幕上的二维码/地址
就是"入口凭证")。

**浏览器防锁屏**:`navigator.wakeLock` 要求安全上下文(https / localhost),我们的页面是局域网
`http://`,拿不到该 API;因此用**静音循环媒体**(muted + playsinline 的极小视频/音频)尽力而为,
页面同时提示"把手机自动锁屏时间调长"。真正的兜底是**分块上传可续传**:万一锁屏被杀,
重新打开页面会从主机记录的偏移继续,不需要重传。

**任务互斥与软键盘**:同一时刻只跑**一个**安装任务 —— 下载(模式 1)进行中不再接受上传;
并且**只在没有任务进行时才提供"输入 URL"入口**。原因是软键盘本身是另一个 LibraryApplet,
弹出期间我们的界面与网络线程会暂停,正在跑的传输会卡住/超时。这条要在真机上确认一次
(`swkbdShow` 返回后界面与传输能立刻恢复)。另一个从参考实现抄来的注意事项:软键盘的
header / 副文案长度受 `len_max` 限制,文案别写太长。

## 9. 前置检查

| 检查 | 判据 | 失败处理 |
|---|---|---|
| **网络可用(上传来源)** | `nifmGetCurrentIpAddress` 拿到一个非 0 的本机地址(手机热点、或与手机/电脑同一个 Wi-Fi 都算) | 停在安装页:**不出地址、不出二维码**,提示"先在系统设置里连上网络(手机热点或同一个 Wi-Fi)";`A` 重新检测 |
| **下载地址支持 Range** | 用 `Range: bytes=0-0` 探一次:必须回 **206** 且带 `Content-Range: bytes 0-0/<总大小>`。这条同时是**容器总大小的唯一来源**;返回 200(服务端忽略 Range,libcurl 不报错,会把整个文件从 0 开始喂给我们)或 4xx/5xx 都算失败 | **直接拒绝**,提示"这个地址不支持断点续传,请换一个地址,或用手机上传";不建占位 |
| 跳过的判定 | 取到 CNMT 后立刻比较:同版本且内容都在 → 跳过;本机已有更高版本且不允许降级(默认) → 跳过 | **不启动传输**,直接进结果页的跳过态 |
| 容器可识别 | magic / 扩展名匹配到支持的容器 | 拒绝并说明"不认识这个文件" |
| 内容清单可解析 | 能列出内容与总大小 | 拒绝 |
| 系统密钥代次 | **不做这个检查**(与参考实现一致) | —— 参考实现也不查 keygen 与主机代次的关系:要求更高固件的包会照装,启动时由控制台自己失败。我们只解析并留着这个数字(日志口径),拒绝的话会误伤"主机拿得到密钥、只是标了高代次"的包 |
| **目标游戏未在运行** | 用 `pmdmntGetApplicationProcessId` + `pminfoGetProgramId` 拿到正在运行的 application 的 program id;它属于**本次要装的 title**(本体 / 更新 / DLC 任一)时判失败 —— 收尾要删同 title 的旧版本,游戏挂在后台也算"在用" | **拦下,不执行安装**,提示"请先完全退出游戏(回主页,在游戏上按 X →「关闭」)再回来";`A` 重新检测 |
| 目标存储 + 空间 | 默认 SD;先算"这次真正要写进目标存储的字节数"(规则见下一小节),SD 不够 → 询问是否装到机身(NAND),NAND 也不够 → 拒绝并给出还差多少;用户拒绝装机身则中止。**这一条尚未落地**(现在只有页眉那两条存储条在显示数字,引擎里没有这道门) | 询问或拒绝,**在开始接收之前** |
| 占位可建 | 逐个 `CreatePlaceHolder(内容大小)`(在开始接收之前) | 中止,不浪费流量 |
| 票据 | 包里的 `<rights id>.tik` + `.cert` **成对全部导入**(缺证书直接拒绝,与参考实现一致);公共票原样导入,个人票也原样导入交给 `es` 判断(它认设备号);**不做"转公共票"** | 包里有"需要标题密钥的内容"却没带票时:**只写日志**继续装(卡带 dump 无票也合法,控制台往往已持有票),日志行 `a content needs title key …` 就是判别依据 |

### 9.1 空间检查:按安装格式的规则

**先说清"参考实现怎么做"**:sphaira 的安装路径里**没有**空间预检查(它直接建占位,不够就失败),它的空闲空间查询只用于 dump 路径与界面显示;nxdumptool 那一类工具也是"空闲 > 文件大小"这一条。所以本节的
规则不是照抄,而是从**平台事实**推出来的;文档此前那句"照参考实现的空间算法(16 KB + 簇)"属于二手
转述,已作废。

平台事实(决定规则的只有四条):

1. `ncmContentStorageCreatePlaceHolder(id, size)` 会**先按 size 建占位文件**(目标存储的
   `placehld` 目录) —— 这一步是硬门:空间不够就直接失败,后续 `Register` 只是把占位移进 `registered`,
   不再要新空间;所以"空间检查"就是"能不能把这次要写的占位都建出来";
2. 占位的大小必须等于**内容自己声明的 NCA 大小**(NCA 头里的 `size`),不是容器里那个文件的字节数;
3. 内容存储是**内容寻址**的:已经在本机的内容(`Has(content_id)`,按**目标存储**问)不会重写,一分钱不占;
4. 元数据库、票据、我们自己的 `log.txt`/`state.json` 都是 KB~MB 级,给个固定余量即可。

**规则(写成一句话)**:目标存储的空闲 ≥ Σ(本次要写在该存储上的内容的 **NCA 声明大小**) + 每内容
一点目录/簇余量(FAT32/exFAT 的簇松弛,以及 > 4 GiB 内容被切成拼接文件时每片一个目录项) + 固定余量;
不够就问机身,机身也不够就报"还差多少"。

**按格式的差异(整理,重点是"哪个数字算数")**:

| 格式 | 容器里存的是什么 | 算进**存储**(要写占位)的 | 算进**流量**(下载/上传要传的) | 要注意的 |
|---|---|---|---|---|
| **NSP** | NCA 明文 + `.tik` / `.cert` | 每个内容的 NCA 声明大小 | 同左(本机文件来源没有流量) | `.tik`/`.cert` 不是内容,不占内容存储;票据交给 `es`,可忽略 |
| **NSZ** | 大 NCA 换成 `.ncz`(zstd),小的仍是 `.nca` | **解压后的 NCA 大小**(NCZ 表 + NCA 头) | **卡上/网络上那个 `.ncz` 的字节数** | 存储 ≫ 流量:300 MB 的文件要占 386 MB;确认页"大小"给的是**存储**口径,进度条的"已传/剩余"给的是**写入**口径 |
| **XCI** | root HFS0(`update`/`secure`/`normal`/`logo`)→ 每个分区又是 HFS0 → 里面是文件 | **只算 `secure` 分区里的内容**;卡带镜像里的 NCA 可能被**对齐填充**,以 **NCA 头声明的大小**为准 | 同左 | `update`/`normal`/`logo` 三个分区**不装**(参考实现也只装 `secure`),不进任何口径;distribution 位改写发生在占位里,不改大小 |
| **XCZ** | 同 XCI,但 `secure` 里可压缩的 NCA 换成 `.ncz` | **解压后的 NCA 大小**(与 NSZ 同源) | `.ncz` 的字节数 | 同 NSZ + 同 XCI;`.cnmt.ncz` 这类"连 meta 都被压缩"的包,meta 也按解压后算 |
| **`.msp`** | 不是容器,识别阶段就拒绝 | —— | —— | 不需要空间检查 |

**与"跳过已有内容"共用同一个判据**:`Has(content_id)`(目标存储),所以"这次要写的"= 任务里**没有**被
标记 `skipped` 的内容;多份 meta 共享的内容(整合镜像"1G+1U+2D"里更新复用本体数据)**只算一次**
(任务表本身就已经去重,见第 33 条);delta 分片从不下载,也不算。

**续传时必须扣掉已经占住的部分**:一次被中断的安装会把"已收到的字节"留在**占位**里(占位还在
`placehld`,没有变成内容),这时 `Has(content_id)` 仍是 false —— 空间检查要把每个占位**已经写进去的
字节数**从这次需求里减掉,否则续传会被误判成"空间不够"。这条和"取消 = 删占位 + 清进度"是同一套
语义的两面(第 10 节)。

**检查时机**:三种来源都一样 —— **确认页之后、第一个字节之前**;下载/上传来源还要更早一步(见第 4 节
的顺序),避免"传了几个 GB 才发现装不下"。

**尺寸口径(两条都已落地)**——占位、进度与将来那道空间门用的是同一个数字:

- **普通内容以 NCA 头声明的 size 为准**(解析时读一次头;与容器表项不一致时按头走并写日志,表项只作
  兜底):参考实现建占位用的就是这个数(`write_size = header.size`),容器表项只是"文件占多少",
  被对齐填充过的卡带镜像会差一点(已核的四个真实包里两者相等)。
- **压缩内容同样以 NCA 头声明的 size 为准**(分节末端只作兜底),所以 NSZ/XCZ 的存储口径从解析阶段起
  就是解压后的真实大小(第 36 条)。

**仍未落地的一条:这道空间门本身**。现在只有界面上的两条存储条(`ContentInstaller::Space()` 被页眉
调用),引擎里没有"要写多少 vs 空闲多少"的判定 —— SD 装不下时不会询问装机身,而是等到
`CreatePlaceHolder` 失败才报错。落地时照这四条写,不必再重新判断:

1. **需求** = Σ(本次要写的内容的 **NCA 声明大小**) − Σ(对应占位**已经写入**的字节数);被跳过
   (`skipped`)的内容不算,多份 meta 共享的内容只算一次,delta 分片不算;
2. **余量** = 每内容一点目录/簇余量(FAT32/exFAT 的簇松弛,> 4 GiB 内容被切成拼接文件时每片一个目录
   项)+ 固定余量(元数据库、票据、`log.txt`/`state.json` 都是 KB~MB 级);
3. **判定**:目标存储空闲 ≥ 需求 + 余量 → 直接开始;不够 → 询问装机身(`Ⓐ 装到机身` / `Ⓑ 取消`);
   机身也不够 → 拒绝并给出"还差多少";选机身则把目标存储换成 NAND 接着走,不退出安装页;
4. **位置**:确认页之后、第一个字节之前,与其它前置检查同一屏(本节开头那条顺序)。

这些检查都在**取到 CNMT 之后**跑,所以实际顺序是:网络 → (下载来源)Range 探测 → 容器头部 →
CNMT → 跳过判定 → 确认页 → 检查(游戏是否在运行 / 空间 / 占位 / 票据)→ 取数据;
而"空间检查"与"跳过已有内容"共用同一个 `Has(content)`(同一目标存储,见第 11 节)。
(keygen 那一行按上表**不做检查**;已实现的检查是"目标游戏未在运行""占位可建"与跳过判定,
空间门尚未落地、票据走"原样导入 + 缺票只记日志"。)

**除"跳过"之外,所有检查失败都停在同一张卡上**:标题就是原因(一句话),下面一行给"怎么办",
页脚 `Ⓐ 重试` / `Ⓑ 返回` —— 用户把游戏关掉、把网络连上、把地址换成一个支持 Range 的之后按一下 `A`
就能接着走,不必退出安装页重来。唯一的例外是"空间不足"(§9.1 落地后):那一屏是**询问**
(`Ⓐ 装到机身` / `Ⓑ 取消`),不是报错。

## 10. 状态文件、续传与清理

当前安装任务的状态写在 `/switch/ACNH-Manager/install-task.json`(与 `state.json` 分开:
后者是 agent 安装记录,卸载 agent 会删掉它)。

字段:`schema`、`source`(file / http-client / http-server)、`container`、`taskId`、
`containerSize`(容器总大小;续传时用来确认用户重新选的是同一个文件)、
`contents[]{contentId, placeholderId, written}`(各内容的取得进度;取数顺序由服务端决定,所以不记"整包偏移")、
`containerState`(解析进度:已读到的目录项、待处理项)、`ticketRightsId`、`ticketImported`。

| 情形 | 语义 |
|---|---|
| 用户主动取消 | **只发生在收尾之前**(见第 4 节)。做的动作:删掉本次建的全部占位、删掉本次已经 `Register` 的内容(含 meta 内容,按 content id 删)、删状态文件、清中间产物 —— 目标是"回到安装前",下次从一个干净环境开始 |
| 结构性失败(容器解析中断、票据缺失、`Register` 失败等) | 等同取消:删上面那些东西、清状态、报错,不留下半个内容 |
| 票据 | **导入过的票据撤不回来**:`es` 没有"删票据"的接口,而且同一 rights id 的 common 票据本来就该长期留在机器上(别的安装也用它)。取消语义里如实说明这点,不假装能清干净 |
| 异常中断(断网、浏览器被关闭/杀掉、手机锁屏、崩溃、断电) | **保留**状态与占位,任务转为"已中断(等待续传)";下次进入安装页时显示"**未完成的安装(已接收 X% / Y GB)**,占用 Z GB",并提供【继续】【放弃(清理)】 |
| 上传中浏览器被关掉 | 连接断开主机**立刻知道**(TCP FIN/RST 或读超时)→ 转"已中断";重开页面后**重新选一次同一个文件**即可从断点续传(用 `task id` + 期望 offset + `containerSize` 三重确认是同一个文件;最终仍由内容级校验兜底) |
| 下载来源(模式 1)的"继续" | **不需要用户重新提供任何东西**(URL 记在 `install-task.json` 里),直接续传;只有上传来源才需要重选同一个文件(见上一行) |
| 下载中(模式 1)浏览器被关掉 | **与浏览器无关**:下载由主机自己的 libcurl 驱动,继续跑;进度在新开的页面或主机屏幕上照常可见 |
| 占位被系统清掉(重启/清理)后恢复任务 | 恢复前逐个 `HasPlaceHolder` 校验:缺了就**从偏移 0 重新开始**(不报错、不写坏),而不是假设占位还在 |
| 未完成任务的可见性 | 安装页**与详情页**都显示"未完成的安装(占用 X GB)"与【放弃(清理)】,否则用户只会看到 SD 空间莫名少了几个 GB |
| 超时自动清理 | **不做**(既定取舍):任务一直保留(含跨应用重启),由用户显式选择"放弃" |
| 在安装页按 `B` | 无任务、服务端未监听 → 直接回上一页;否则**先让用户确认**;确认后销毁服务端并中断传输(已收数据保留、下次可续传)。**收尾阶段(⑨ 之后)不弹这个确认**:那一段不能取消,`B` 在收尾期间不响应 |

清理只针对自己记录的东西(占位 id + 我们自己注册的 meta 内容),**不使用**
`ncmContentStorageCleanupAllPlaceHolder`(会波及别的工具的安装)。

**落地现状(2026-10-15)**:

- ✅ **本次运行内的取消/回滚**已实现并真机验过(删占位、删本次已 `Register` 的内容、票据撤不回也
  如实说明);**不使用** `CleanupAllPlaceHolder` 这条也照做。
- ✅ 任务文件的**序列化/解析**(`Schema`/`TaskId`/各内容 `written`/`containerSize` 等字段)已实现,
  并有主机用例;`install_task.*` 也按"续传必须是同一个文件"的判定钉住了。
- ❌ **任务文件从没落盘**:引擎里没有任何读写它的代码(`install-task.json` 只在纯逻辑层出现),
  于是上表里"异常中断 → 保留状态 → 下次显示未完成的任务 → 继续/放弃"整块**没有落地**。
  现实后果:安装中途崩溃/断电/强杀之后,**占位会留在目标存储的 `placehld` 里占着空间**,
  界面上看不到(首页那句 `InstallPending`"未完成的安装(已接收 %s)"文案已经备好但没人调用),
  下一次安装也不会复用它 —— 只能靠重新装一遍(或别的工具清理占位)把空间要回来。
  这一条与 §9.1 的空间门是同一类问题(都关乎"空间去哪了"),建议挨着做。

## 14. 风险与已定稿的取舍

| 项 | 说明 |
|---|---|
| 商店收录与定位 | 通用安装器"能装游戏本体",与官方 Homebrew 商店的收录口径可能冲突(需要在 README/商店文案里如实说明"本工具不提供任何游戏内容";分发定位问题因为"不托管"而消失,该项风险**已消除**) |
| 浏览器长传输 | 锁屏/切后台被浏览器杀是常态;用静音媒体尽力避免,靠分块续传兜底(T8) |
| FAT32 与 > 4 GiB 的包 | 平台在 FAT32 上放 > 4 GiB 东西的办法是**拼接文件**(concatenation file):libnx 里就是 `FsCreateOption_BigFile`("Creates a ConcatenationFile (dir with archive order) instead of file"),`fs` 把它**呈现成一个文件**(程序看到的是一个 4.65 GB 的 `.nsp`,大小是各分片之和),底下是**一个带属性的目录 + 编号分片 `00`/`01`…**,每片都压在 4 GiB 以下。真机探针实测(卡上那份 DBI 上传的 3.0.3 包):`…nsp/00` = 4,294,901,760 字节、`…nsp/01` = 355,338,011 字节,和 = 4,650,239,771 = 控制台报的"单文件"大小;`fsFsCreateFile(path, 0, FsCreateOption_BigFile)` + `fsFileSetSize(4.5 GB)` 两步都成功。**普通文件则写不过去**:真机上顺序写会在正好 4 GiB(4,290,772,992 + 4 MiB = 4,294,967,296)处被拒,`fsFileSetSize(4.5 GB)` 也被拒(0xA86F7202 / 0xA8AF7202)——sys-agent 的 FTP、sphaira 的文件传输就是建了普通文件,所以在 4 GiB 处"到最后失败"。**对安装器的影响**:读取路径把拼接文件当普通文件,所以"本机文件"来源照样能装这种包(真机上那页确认页显示 3.0.3 / 4.3 GB 用的就是它);我们要写大文件时也有这条 API 可用,但本设计不往卡上留包,**不做界面检查** |
| MSP 与应用自带文件冲突 | 因为**不做 MSP**,该项风险直接消失(第 7 节) |
| 服务端薄层自研 | 报文解析用 picohttpparser(MIT),但 accept / 读循环 / 路由 / 生命周期是我们自己的代码 —— 需要主机测试覆盖可脱离 socket 的逻辑,并在真机验证 4.65 GB 上传、断线续传、重复块不乱写与长时间不断线(T7、T8、T18) |

**已定稿的取舍(记录在此,避免后人重新判断)**:

1. **校验与安装选项逐项跟随参考实现的默认值**:包含"默认跳过 NCA 哈希校验"与"默认跳过 NCA 头
   验签"。接受其后果:损坏的下载与第三方改造内容都会照装不误,能否运行取决于用户自己的系统。
   **界面不为"跳过了校验"加任何额外提示**——参考实现怎么做,我们就怎么做。
2. **"改造型"选项的默认值照抄,但只实现一半**:distribution bit 按需改造(XCI 装本体必需)、

   转换"的规矩处理,并且读到的任何密钥材料**永不写进日志、界面或输出**(本仓库对密钥的纪律)。
3. **不支持 MSP(mod 包)**;`.msp` 在识别阶段直接拒绝并建议用支持它的工具安装。
4. **首页 `Unsupported` 态**:主按钮「安装游戏更新」+ 副标题「升级完会自动安装 agent」。
5. **入口**:页眉右侧常驻第 4 项 **「游戏安装/更新」**(`Game Install / Update`,快捷键 **`＋`**),
   **「功能说明」的快捷键相应改为 `－`**;首页那个按钮只是同一页的上下文快捷入口,

6. **安装页是模态页**:进入后页眉其它入口一律不可用,只保留本页动作与 **`B` 返回**;
   有任务或服务端在监听时按 `B` 要二次确认。设计意图是"安装时只做安装这一件事"。
7. **进度显示照参考实现样式**:条形进度 + 百分比、当前内容文件名、已传/剩余字节、估算剩余时间、
   阶段文案与"第 N/M 个内容",页面顶部显示目标存储剩余空间;显示包里的游戏名(NACP 文本)+
   版本 + 类型,**以及包自身那张封面**——当初写"不显示游戏图标"的理由是那时没有 JPEG 解码器,
   现在它已经在确认页上用着,于是进度页与结果页也一起给,长时间传输里"这是什么"不必靠猜;
   **不做"关闭屏幕"**(那要多一套按键语义,1.1.0 不做)。
8. **任务互斥与多标签页**:活动 = 主机侧唯一任务(不是标签页);推进类请求要带 **task id + 期望
   offset**,不匹配即 **409**;`/status.json` 只读,所有页面都能看进度,只有持有当前 task id 的页面
   能推进。观察者页面**可以取消,但必须二次确认**。
9. **异常中断一律保留进度,不自动清理**:浏览器被杀、断网、锁屏、崩溃、断电都转"已中断",已收数据
   与占位保留;重开页面重新选同一个文件即可续传(占位若被系统清掉则从 0 重来);
   安装页与详情页显示"未完成的安装(占用 X GB)"+【放弃(清理)】,**不做超时自动清理**。
10. **安装选项不做界面(方案 A)**:1.1.0 里这些选项固定跟随参考实现的默认值,安装页不给开关,
    **详情页也不列出**;引擎侧仍把它们实现成一个**带默认值的选项结构**,将来若要可改,只需补
    "列表控件 + 两列文案"两块(照参考实现搬全 19 项约 2–3 天;只暴露安全子集约 1–1.5 天),

11. **安装页带存储指示条**:microSD 与系统两条,数字给**可用 / 总**(内容存储口径,与前置检查同源),

    那条路要先落盘几个 GB 临时文件,与本方案"边收边写占位"的整个前提冲突。
23. **网络可用是"上传安装"的前置条件**:没连网(手机热点或与手机/电脑同一个 Wi-Fi 都算)时
    不出地址、不出二维码,只提示去系统设置连网;`A` 重新检测。
24. **目标游戏正在运行就拦下**:判据是"正在运行的 application 的 program id 属于本次要装的
    title(本体 / 更新 / DLC)",因为收尾要删同 title 的旧版本;提示用户回主页把游戏完全关掉,
    再按 `A` 重新检测。**不提供"替用户关闭游戏"的动作** —— 那属于另一个应用的会话,
    我们不去碰。
25. **取消只发生在收尾之前**:从第一个 `Register` 起就不再接受取消(屏幕上显示"正在收尾"),
    因为"删旧版本 + 写元数据库"必须一次做完;取消时除了删占位,还要删掉本次已经 `Register`
    的内容;**导入过的票据撤不回来**(`es` 没有删票据的接口,同一 rights id 的 common 票据
    本来就该留着),这条如实写进语义,不假装能清干净。
26. **三个入口卡片可点**:选来源那一屏的卡片触摸与按键等价;确认页、进度页、结果页不设可点控件。
27. **页面全部内嵌**:`data/installer_page.html.bin` 是自包含的单文件(内联 CSS/JS,不引用任何
    外部资源),因为主机常常只有手机热点、没有外网,任何外链都会让页面白屏。
28. **"在手机上粘网址"是下载来源的主入口**(随 M4 一起落地;在它之前,下载来源只有主机软键盘这一条
    入口):`X 下载安装` 与 `A 上传安装` 落到**同一块来源屏**(地址 + 二维码 + 等待连接),网页同时
    提供"选择文件"与"粘贴下载网址"两个入口;主机侧只是按来源换标题与提示语,页脚统一给
    `A 在主机上输入网址`(软键盘为备用入口)。页面提交地址走 `POST /url`(只校验 scheme 与长度,
    不解析),主机把任务从 `http-server` 切成 `http-client`,一个任务同一时刻只有一个来源。
29. **有任务时服务端不销毁**:服务端活到"出结果页"或"退出安装页"为止,否则手机页面立刻失联、
    看不到也取消不了。页面自己不记状态 —— 每次打开先读 `/status.json`,由主机告诉它现在该显示
    哪一屏(等待来源 / 只读观察 / 传输中 / 已结束),刷新、换设备、断线重连都走同一条路。
30. **入口保持三张卡**(`Y 本机文件` / `X 下载安装` / `A 上传安装`):虽然 X 与 A 落到同一块来源屏、
    网页上两个入口也都提供,分开仍然更贴合用户此刻的想法;合并成两张更"干净",但少了一层"我
    要干什么"的表达。**决定:不合并。**
31. **游戏名用 App 界面语言,主机系统语言的写法另起一行**:NACP 里一个标题最多带 16 种语言的写法,
    而 `nacpGetLanguageEntry()` 回答的是**主机系统语言**那一种 —— App 设成英文、主机是中文时,
    确认页显示的是中文游戏名,读起来像 App 忽略了语言设置(真机反馈)。规则:主行取 App 当前界面
    语言的写法,主机给的名字与它不同时,在标题下用小一号的灰字再给一行(桌面/相册里显示的就是
    这个名字,两个写法同时出现也正是"同一个游戏"的凭据);两边一样只留一行;App 的语言在包里
    完全没有时,才退回主机给的名字,再退到包里第一个非空写法。判定是纯函数
    `install::ChooseTitleNames()`(`source/install/title_name.hpp`),主机测试钉住。
    名字过长时主行**降一档字号**而不是截断:英文名 "Animal Crossing: New Horizons" 在 40 px 下
    比卡片留出的宽度多几个像素,原先总是以省略号结尾。
32. **装完受支持的本体/更新后自动安装 agent**(用户 2026-10-14 改变策略,取代原先"两件事分开、
    由用户自己按"的决定):玩家要的是"装个游戏 → 能用聊天码",所以第二半不再等他。
    触发条件只有一条:**这次运行结束时控制台上的版本是清单里支持的版本** —— 本体与更新(
    `MetaTypeCarriesGameVersion()`)**且** `AgentSupportedFor()` 为真。于是:追加内容与数据补丁
    不触发(它们不改版本)、不是我们的标题不触发、不受支持的版本不触发(那种情况确认页已经说明
    为什么)。第二半走的路径与首页按钮**完全相同**(同一份清单、同一个 payload 来源、同一个引擎),
    所以"记录 → 修复 → 已是最新"的判定天然一致;区别只在:它不换页、进度卡换成"正在安装 agent"、
    失败不吞掉(结果页给一句能照做的提示,原因进 `log.txt` 与详情页)。
    **"已存在的包"这条跳过路径同样触发**:跳过只说明这个包不用再写一遍,控制台上的版本还是那个
    版本,所以第二半照跑(这正是"重装一次顺手把 agent 补齐"的那次)。
33. **容器里有几份 meta 就装几份**,照参考实现的 `InstallInternal`:它遍历容器里的每个 CNMT,对每份
    meta 各自"删旧版本 → 写 meta 记录 → 推记录",本体、更新、每个 DLC 都这样。理由有两个:①整合
    镜像("1G+1U+2D")的意义就是一次装齐,只装本体等于把用户放进包里的更新和 DLC 丢掉;②DLC 的
    记录本来就该挂到它所属游戏的 application id 下,只推本体那份记录,控制台永远不知道追加内容
    存在。落地时的三处细节:
    - **记录里的 meta 内容必须是"这次真正安装的那一份"**:写记录的 blob 第一项是 meta 内容自己,
      而这个名字原先来自纯解析层(它只会取容器里第一个 `.cnmt.nca`,整合包里通常是某个 DLC)。
      名字与实装内容不一致时,控制台按记录找不到那份内容,直接把标题判成"不可用"并拒绝启动
      (真机现象:方块有名字有封面、点进去"无法启动软件";我们自己的自检先报出
      `usable? missing 1 of 5: 6dad0a38…`)。
    - **本体排在第一位**:界面(名字/封面/版本)与控制台的 application 记录都按本体走;CNMT 的类型
      只有在解密的 meta 内容里才看得到,所以"先读全、再排序"是必须的顺序。
    - **界面不许沉默**:确认页的「类型」一栏会把搭车的那几份写出来(「本体 + 更新 ×1 · 追加内容 ×2」),
      版本/名称取的是**生效版本**那份 meta 的控制数据(装了更新就显示更新的版本),agent 的
      "支持不支持这个版本"也按它判断 —— 按本体那份判断会在整合包上得出相反结论。
34. **XCZ 与 NSZ 在内容层面是同一套规则**(照参考实现自检):压缩**只发生在文件那一层** ——
    参考实现自己的 dumper(`NszExport`)把 collections 里每个文件原样写出,只有 `Program` /
    `PublicData` 类型的 `.nca` 会被换成 `.ncz`;**分区头、HFS0 表、meta 内容、control、legal 一律
    原样**。所以"XCZ 的 secure 分区本身被整体压缩"是不成立的:参考实现的 XCI 解析器对 `.xci` 与
    `.xcz` 用**同一个类、同一条代码路径**读分区表,这本身就证明表是明文。据此自检补了三处:
    - **"装进占位再挂载"那条读 CNMT/NACP 的路原先只会原样拷贝**:万一某个包的 meta/control 是
      `.ncz`(参考实现的读侧同时认 `.cnmt.nca` 与 `.cnmt.ncz`,说明这种包确实存在),它会把压缩流
      当 NCA 写进占位,静默产出坏内容。现在这条路径也会解码(表 + 分节再加密,规则与安装路径同源);
    - **`.cnmt.ncz` 的名字原先不认**:纯解析层只找 `.cnmt.nca`,遇到这种包会报"包里没有 meta 内容";
    - **解码后的真实大小改用 NCA 头里声明的 size**(分节末端只作兜底):某个包的最后一段没覆盖到文件
      末尾时,按分节末端算会得到**偏小的占位**,控制台同样答"无法启动软件" —— 与"记录指向没装过的
      内容"是同一类故障。
    另外两处顺带收紧:压缩内容的表读取**由条目决定而不看文件扩展名**(改名过的包也照样解码),以及
    任务表里共享内容只列一次(见第 33 条)。

35. **块表不是装饰,它决定负载怎么切**(2026-10-15,第一个真实 `.xcz` 装不上之后查出来的):
    带块表的 `.ncz` 把负载切成固定**解压**大小的块(末块是 `decompressed_size` 的余数),每块是
    一条独立的 zstd 帧(`nsz_dumper.cpp` 用 `ZSTD_compress2` 逐块压),**压不小的块原样存放**
    ——dumper 在"压缩结果 ≥ 原尺寸"写原字节,读侧的判据就是参考实现的
    `compressed = 块在文件里的体积 < 该块解压后的体积`。两件事必须同时成立,否则读者会把原样块
    当成压缩数据:真机那份 `Super Mario Party Jamboree [0100965017338000][v0][US].xcz` 的 program
    内容就是这样——块大小 1 MiB、5417 块,块 0 是压缩块(945 448 → 1 048 576),块 1、2… 是原样块
    (1 048 576 = 1 048 576),末块 113 843 → 163 840;把整段负载喂给一条 zstd 流会在块 1 立刻报
    `the compressed content could not be decoded`(块 0 那条帧解得很干净,所以日志里看不出前兆)。
    落地方式:表解析多存一个 `block_decompressed_size`,块表相关的三个判定做成纯函数
    (`NczBlockSourceSize` / `NczBlockDecodedSize` / `NczBlockCompressed`),解码收进一个模块
    `install/ncz_decode.*`——**安装传输与"装进占位再读 CNMT/NACP"两条路共用它**(此前是两份各自
    实现的解码循环,同一个 bug 有两处),每块解完还要核对该块解出的字节数是否等于表里声明的数,
    对不上就直接报错,不把半个 NCA 写进占位。

    验证方式(此后作为这类格式问题的标准做法):**先在开发机上用同一份真实文件跑通,再上真机**,
    两个工具都已入库并登记在 `docs/tools-guide.md`——`tools/ncz-probe.sh`(应用自己的解码代码)与
    `tools/ncz-blocks.py`(自带容器解析的独立实现,逐块调 `zstd`)。同一个 `.xcz` 两条路径整份解出
    program 内容,都得到 5 679 251 456 字节、sha256 均为
    `8b4fcc9ca98de420ad868de0f29ed2e0782a762fc070d3332abf9f11023fe498`;主机测试里另有一个自造的
    压缩块 + 原样块 + 半块尾块混合包,单独钉住"原样块必须拷贝"这条规则(主机测试现在也链 zstd)。

36. **四格式对照参考实现的一轮审查(2026-10-15,结论:再补四处)**:拿到真实样本后逐项对照
    `yati.cpp` 的安装/收尾序列与 `nca.hpp` 的字段布局,发现四处"参考实现能做、我们做不到"的差异,
    全部按参考实现补齐:
    - **记录里的"所需系统版本"要清零**(`lower_system_version`,参考实现默认开):它位于
      application / patch 扩展头里 `{u64 id, u32 required_system_version}` 的第二个字段,为零的
      记录在任何固件上都能启动;带着更高版本号的包**装得上但启动会被系统以"需要系统更新"拒绝**。
      我们在 `BuildMetaRecordBlob` 里照参考实现清零(两种 meta 类型都做,扩展头不足 12 字节则不动);
    - **票(.tik/.cert)按 rights id 成对收全**:容器可以带多份票(一个包里有多个加密标题),原先只读
      第一份,现在按 `<rights id>.tik` + `<rights id>.cert` 成对读取、全部导入,缺证书直接拒绝(参考
      实现同样拒绝)。real 样本证实这条路是必需的:ACNH 的更新 NSP 中只有 program 内容是标题密钥
      加密(rights id `01006f8002326800000000000000000b`),靠随包的票才能读;
    - **内容大小以 NCA 头为准**:容器条目是"文件占多少"(HFS0 条目按 0x200 对齐,可能带 padding),
      NCA 头里的 size 才是控制台存下来的内容大小;参考实现用它设占位(`write_size = header.size`)。
      现在每个内容的头都会读一次,与条目大小不一致时按头走并把差异写进日志(已核的四个真实文件里
      两者完全一致,所以这是带日志的兜底,不是行为变更);
    - **gamecard 的 distribution 位对 meta 内容也要改写**:meta 内容走"装进占位再挂载"这条读出路,
      原先不做头改写,而参考实现对**每一个**内容(meta 在内)都做。现在两条写路径共用
      `RewriteDistributionBit`。卡带 dump 的 meta 内容保持 gamecard 也能挂载(实机验证过),所以这条
      同样是"与参考实现装出同样的字节"而不是"今天装不上"。

    同一轮还发现一条**跳过语义**的偏差并修正(与参考实现对齐):"已有更高版本就跳过"只对**更新包**
    成立(`GetLatestVersion` 只对 patch 比较版本),本体与追加内容不受它约束。否则会出现真实故障:
    本体内容被删、更新记录还在时,装本体会被判成"已有更高版本"而跳过,**标题永远修不回来**。跳过的
    第二种情形(同一个版本已经装好且控制台可用)仍然对四种类型都生效,这是"重复安装不重传"的那条。

    有意保留的一处差异:**票的"转公共票"(`convert_to_common_ticket`,参考实现默认开)不做**。它到底
    做什么、需要什么,值得写清楚,因为它常被误传为"必须有 prod.keys":
    - 拿到一张票先**判断要不要改**(`ShouldPatchTicket`):公共票 → 用随包的证书链里的公钥验一次
      RSA-2048-SHA256 签名,**验得过就原样保留**(官方渠道下载的包走的就是这条路,整步是空操作);
      验不过(被改过的票)→ 改;个人票 → 按开关改(默认开)。
    - 改的时候取标题密钥:公共票直接从票里拿(已经是 titlekek 加密态);**个人票用本机 setcal 的设备
      密钥** RSA-OAEP 解(先核对 device id 是否本机),而 setcal 交出来的设备密钥本身是被
      `eticket_rsa_kek` **加密**的——那把 kek 在 `prod.keys` 里。
    - 新票不重签:issuer 改成 `Root-CA00000003-XS00000020`,签名块填 0xFF 占位,标题密钥块、格式版本、
      key generation 与 rights id 照搬,issuer 变了就去控制台自己的证书库取配套证书链,然后照常
      `esImportTicket`。
    - 因此:**官方公共票与 prod.keys 无关**;**个人票**这条路才需要 prod.keys(缺文件时不是"开局就报",
      而是翻到取标题密钥那一步才失败);`convert_to_standard_crypto` / `lower_master_key` 这两个开关
      才是真正离不开 prod.keys 的(titlekek / key_area_key / master_key),而它们的默认值是关。
    本 App 的选择是**原样导入票**并交给 `es` 判断:官方包与参考实现结果一致(ACNH 的更新包就是这么装
    的,实机可运行);个人票若本就是为本机签发,原样导入通常即可用,若来自别的主机则谁都救不了——转公共
    票用的也是**本机**设备密钥,device id 不匹配同样失败。日志里的 `tickets N of M imported` 与
    "a content needs title key …" 两行就是判别依据。

    同轮补的两处:
    - **压缩内容的占位大小改为"以 NCA 头声明的 size 为准"**(分节末端只作兜底):此前取两者较大值,
