## 状态与设置(2026-09-18)

两件都在真机上按上面的矩阵验过,补充两点实现事实:

- `Plan()` 只比较**安装记录与清单**,不看卡;卡上是否真有那些文件由
  `install::VerifyInstalledFiles()` 在每次 `Collect()` 之后核对(存在 + sha256 一致),不一致即报
  `HomeKind::Incomplete`。它只在计划本来是 `UpToDate` 时生效,不会覆盖"该装 / 该修"的判定。
- 界面语言存 `/switch/ACNH-Manager/settings.json`(与 `state.json` 分开,因为卸载会删掉后者)。
  文件缺失或损坏都退回默认语言,并把原因写进 `log.txt`,不挡启动。

测试提醒:用 sys-agent 的 FTP 给目录**改名**时,同一路径可能又出现(实测 `RNTO` 之后 `exefs`
与 `exefs-hidden` 同时存在),所以模拟"文件消失"请用**删除**(先删文件再 `RMD` 目录)。

## 崩溃记录(2026-09-17)

`/atmosphere/crash_reports/` 里只有 12:18–12:26 的四份报告,进程都是 `hbloader`
(`010000000000100d`),死因是写越界(Data Abort),对应"按 + / 进游戏就整机重启"。
根因是绘制高度用了 `height_aligned`(768 行)而线性影子缓冲只有窗口高度(720 行),
每帧越界写堆 48 行、约 245 KB,破坏与加载器共享的进程堆(见 `docs/architecture.md` §7)。
改成按 `win->height` 绘制后,同一台机器上反复启动、翻页、切语言、退出都没有再产生新报告;
历史日志里 04:47 与 04:51 两次构建的运行都以 `app: exiting` 正常收尾。
注意:从 Home 挂起再重新启动时,applet 是被外部结束的,日志会停在
`ui: init ok` 而没有退出行 —— 这不等于崩溃,要和"收尾缺行 + 有新崩溃报告"区分开。

**崩溃证据从哪来、要不要留**:现场在卡上 —— `/atmosphere/crash_reports/*.log`(Atmosphère
的文本报告:进程名/Program ID、异常类型与地址、栈回溯)和 `/atmosphere/erpt_reports/*.bin`
(同一批错误的 ERPT 二进制记录),排查时用 sys-agent 的 FTP 取回即可,不必留副本。我们撞到的
那一份长这样:`Process Name: hbloader`、`Program ID: 010000000000100d`、`Type: Data Abort`、
`Result: 0x4A8 (2168-0002)`,出错地址远离我们自己的缓冲。看到"hbloader + Data Abort"的报告,
先查上面这两条(绘制高度 clamp、退出模式),再怀疑卡或系统服务。

## 装到游戏目录的实测结论(2026-09-17)

- **applet 模式可以写 SD 卡,包括 `/atmosphere/contents/<tid>/exefs/`**:写盘探针在游戏目录里
  完成 create→SetSize→write→flush→read→delete 全部返回 0;不需要为了写盘去要 application 模式。
- **`fs*` 只接受绝对路径**:同一探针里,`switch/...` 与 `atmosphere/...` 两种相对写法都在
  `create` 上返回 `0x002EEA02`。这与"干跑 3/3 通过、真装第一步就失败"的现象完全对应,
  细节见 `docs/architecture.md` §4.1。
- 装完后 `exefs/` 三个文件的 sha256 与发布清单逐字一致(`subsdk9` 74 062 B、
  `main.npdm` 1 652 B、`acnh-agent.version` 219 B),`/switch/ACNH-Manager/state.json` 记录了
  agent 版本/commit/contentId/buildId 与三个文件的 size+sha256,可用于卸载回滚。

## 触摸输入实测(2026-09-17)

用 `/switch/ACNH-Manager/dev-touchprobe` 开关在真机上验证(hid 共享内存 + 触点坐标):

```
touch probe: hid shared memory ready
touch probe: down at x=1217 y=51 count=1 diameter=67x89
touch probe: released at x=1213 y=56
```

- **applet 模式可以读触摸**:`hidInitializeTouchScreen()` 成功、共享内存就绪(与 Sphaira 的用法一致);
  触摸因此在设置里是"能用就用、不能用就退回按键",不是必需能力。
- **`HidTouchState.x/y` 就是 1280×720 屏幕坐标**:手指点在右上角,记录值与位置吻合,无需面板坐标换算。
- 指腹接触面约 `67×89` px → 可点目标做到 100 px 以上、间距 ≥ 20 px 才不至于误触。
- 注意:`hidInitializeTouchScreen()` 在失败时会 **abort 整个进程**(libnx 行为),所以它只在这条
  探针路径与 `ui::Touch::Init()` 里各调用一次,其余地方先查共享内存再读状态。

## 退出路径:相册黑屏与修复(2026-09-17)

现象与定位(同一相册会话,同一份 NRO,只有"是否走 applet 退出命令"这一个变量):

| 构建 | 第 1 次退出 | 第 2 次退出 | 第 3 次退出 |
|---|---|---|---|
| `__nx_applet_exit_mode = 0`(返回加载器菜单) | 正常 | 正常 | **相册黑屏**,进程仍在,按 Home 后黑屏/白屏 |
| `__nx_applet_exit_mode = 1`(终止 applet,回主界面) | 正常 | 正常 | 正常 |

- 黑屏时应用侧日志完整(`ui: loop exited` → `app: exiting`),`sysagent system process-list`
  里 `010000000000100D`(hbl/相册)仍在,`capssc` 截屏全黑 → 不是崩溃,是显示资源耗尽。
- 与触摸无关:同一份二进制加/不加触摸初始化都能正常退出,黑屏只跟"同一相册会话里第几次
  启动/退出"有关。机制与取舍见 `docs/architecture.md` §10。
- 修复后的验收(2026-09-17 23:2x,`src:2bfd8b92` + exit mode 修复,`acnh-manager.nro`
  sha256 `5af1f9ce…`):连续 6 轮"Home → 相册 → Sphaira → ACNH-Manager → B 退出",每轮都用
  日志确认应用真的跑起来画过帧(`ui: first frame done`),每轮退出都干净回到主界面,无黑屏、
  无崩溃报告;对比基线(修复前)在第 3 次退出即黑屏。

## 触摸点击失效与修复(2026-09-18)

真机复现:首页"重新安装"按钮用手指点击**毫无反应**(截屏前后差异 0.0%),但 `+`/`B`/方向键
一切正常——也就是触摸被读到、却没有触发动作。

原因在按下的"松开帧":`hidGetTouchScreenStates` **只在手指接触时给出坐标**,松开那一帧
`state.count == 0`,`ui::Touch::Poll()` 于是返回 false 且不写 x/y,而调用方拿这次(全 0 的)
坐标去和按下点比对距离,于是每次点击都被当成"拖出屏幕一大截"的滑动而丢弃。

修复:把判定收进 `source/ui/action.hpp` 的 `TapTracker`——按下时记住动作与落点,手指在
按下期间持续记录最后坐标与最大偏移,松手时要求"全程偏移 ≤ 32 px"且"抬手点仍落在同一个
启用动作上"才触发;`tests/host_tests.cpp` 用 5 组用例把这条规则钉住(含"拖出去再拖回来
不触发")。

真机验收(2026-09-18,`acnh-manager.nro` sha256 `d8550268…`):

| 手势 | 屏幕变化 | 结果 |
|---|---|---|
| 点击首页"重新安装"(640,341) | 30.0% | 进入"安装确认"页(修复前同一手势 0.0%) |
| 从该按钮拖到 (300,650) 后松手 | 0.0% | 不触发任何动作(滑动不会误触按钮) |

## 安装的原子性与故障注入(2026-09-18)

起因:连续"安装 → 卸载 → 安装"时,第二次安装死在 `backup …/main.npdm rc=0x0000D401`,并且
**把已装好的目录改成了半成品**(只剩 `subsdk9`,另外两个文件不见了)。

修复(`source/install/engine.cpp`):安装改成两阶段——`PrepareFile` 只写 `<目标>.acnh-tmp` 并回读
校验(不碰已装文件),全部就绪后 `CommitFile` 才逐个"备份 `.acnh-old` → rename 落位";提交阶段

### 路径贴着映射边界:`0xD401` 的真根因(2026-09-18,已修复)

现象:某些序列之后,**同一个应用会话里的后续安装 / 卸载一律失败**,错误码都是 `0xD401`,而且每次
失败的步骤都不一样(`mkdir …/01006F8002326000` → `create …/subsdk9.acnh-tmp` →
`open …/subsdk9.acnh-tmp` → `rename into …/subsdk9` 都出现过);同样这几步在**新开的会话里必然成功**,
酷似"这个进程跟存储卡失联了"。最早是 T1a 用例里单独撞见一次(失败原因当时只在屏幕上、日志里
没有,查不到现场),因此先给 `Install()`/`Uninstall()` 补了 `install: ok=… error=…` 日志行,再按
日志把复现步骤定下来:

1. 退出应用 → 重新打开(新的应用会话);
2. 在应用运行期间用 FTP(sys-agent 6001)往卡上写一次这个会话没写过的文件(测试里给
   `exefs/subsdk9` 追加一行);
3. 在应用里卸载(`uninstall: ok=1`);
4. 紧接着安装 → `install: ok=0 … rc=0x0000D401`。

| 排查 | 结果 |
|---|---|
| 目录是否真的没了 | 没有:FTP 能列出 `atmosphere/contents/01006F8002326000`,卡上文件健康 |
| 同一会话内重开 mount(`fsFsClose` + `fsOpenSdCardFileSystem`)后重试 | 无效(仍 `0xD401`,只是失败点后移) |
| 同一会话内重建 fs 会话(`fsExit` + `fsInitialize`)后重试 | 无效 |
| 同一会话内连续重试 4 次 | 全部失败,失败点在不同文件之间漂移 |
| 退出应用、重新打开后再装 | **成功**(启动清理顺手清掉失败留下的 `.acnh-tmp`),记录与卡上文件一致 |
| 去掉第 2 步(不写卡)再走同一序列 | 成功 |

**根因(2026-09-18 定位)**:与卡、与"会话失联"都无关,是**路径字符串在内存里的位置**。
`fs*` 把路径当作声明长度 `FS_MAX_PATH`(0x301)的 IPC 缓冲传出去,服务端按这个长度映射一整段
页对齐窗口;路径落在某个映射末尾 0x301 字节内时,窗口就伸进未映射页,内核返回
`InvalidMemoryState`。设备端逐调用追踪抓到的现场:

```text
fsop: mkdir rc=0x0000D401 ptr=0x329C697E80 region=0x329C674000+0x24000
fsop:   window=0x329C697E80..0x329C698181 region_end=0x329C698000 last_page type=0x0(unmapped)
fsop: mkdir rc=0x00000000 ptr=0x329D99D170 region=0x329D619000+0xF7E7000   # 同一个会话、同一个目录
fsop:   window=0x329D99D170..0x329D99D471 region_end=0x32ACE00000         # 窗口在映射内 → 成功
```

即:窗口越界的那次失败、窗口在界内的那次成功,都发生在同一个会话、同一个目录上,相隔毫秒。
哪个分配落在映射末尾由分配器决定,所以 `std::string` 拼出的路径时好时坏、失败点还会在文件之间
漂移,重启应用后换个位置又好了 —— 这也解释了"外部写卡 + 卸载"这条复现路径为什么时灵时不灵。

**修复**:所有交给 `fs*` 的路径先复制进 `util::FsPath`(`source/util/fs_path.hpp`,长度
`2 × FS_MAX_PATH` 的局部缓冲,窗口不可能越出);引擎、环境探测、主程序、日志与开发开关检查全部
改走它(后两处是 2026-09-20 补的,见文末"路径缓冲规则补完")。规则与实测细节见
`docs/architecture.md` 第 4.2 节。

按同样的证据向 libnx 提过报告(它的 `fsFs*` 把路径缓冲声明成固定 `FS_MAX_PATH`)。上游把那份报告
移到了**非公开仓库**,链接对普通账号不再可见,本仓库因此不再跟踪它的状态;后来从带符号的官方
SDK NSO 得到的结论是:官方客户端把路径拷进自己的 `FS_MAX_PATH` 零填充缓冲、装不下就返回 fs 的
`TooLongPath`(6003),再按完整声明长度发出去 —— 与这里的做法同形(见 `docs/architecture.md`
第 4.2 节)。

**验证**(`acnh-manager.nro` sha256 `a8860c0c…`):原先必失败的复现(全新会话 → 手改 `subsdk9` →
卸载 → 安装)连跑 4 次全部成功(`uninstall: ok=1 files=3` + `install: ok=1 files=3`,记录与卡上
文件一致),其中一次是在**没有** `dev-fsprobe` 开关的情况下跑的;四个故障注入用例全绿;修复前同一
脚本 6 次全部失败。

结果页仍保留一行兜底提示(`ResultRelinkHint`):万一再出现这个错误签名,「管理器与存储卡失去
联系:退出本程序后重新打开,再试一次」是实测有效的恢复动作。

## 联网检查与一键更新(2026-09-19)

这一轮把"检查更新"从"只提示版本"变成"能下载并安装新版",同时把检查挪到工作线程上,
并加了一次启动静默检查。验收方式、证据与当时的网络状况如下。

**托管端**:今天这台机器的网络**连不上当时的发布托管端**,
所以正路线是用**本机 HTTPS 镜像**(自签证书、`agent-manifest.json` + `.sig` + 三个 payload 文件)
验的:一台 Mac 起静态服务,临时把 `kDefaultManifestUrl` 指向它,构建测试用 NRO 部署到真机;
验完把地址改回正式托管地址重新构建(`tools/verify-release.py --nro` 核对构建戳来自当前源码树)。
托管端上那条正路(取清单 → 验签 → 一键更新)因此**只验到了传输层**:同一份代码、同一个域名,
区别只在托管端连通性;换托管方后按同样的用例补验(见下面"托管端迁移到 Gitee"一节)。

一次成功检查的日志形状(镜像在 `https://<局域网 IP>:9443/`,清单 `0.11.1`):

```
update check: started (url=…/agent-manifest.json)     ← 工作线程起来了
update check: manifest ok, agent 0.11.1               ← 清单 + .sig 都取到、验签通过、解析通过
install: ok=1 files=3                                 ← 一键更新:三个文件按清单 size/sha256 校验后落盘
```

失败与边界:

| 情形 | 现象 |
|---|---|
| 托管端连不上 | 副标题"检查失败: 网络不可用",日志 `Couldn't connect to server`;启动那次静默检查不打扰用户 |
| 清单被改但没重签 | 副标题"检查失败: 清单签名校验失败",日志 `signature does not match rc=-0x4E00` |
| 只有清单没有 `.sig` | 日志 `no signature (HTTP 404)` |
| 工作线程建不起来 | 修复前:日志 `threadCreate rc=0x00001759`、按 `X` 毫无反应;现在按"检查失败: 应用内部错误"上报,详情页与日志带原始 `rc` |
| 检查期间操作 | 界面照常响应:spinner 在转、可切页、可退出 |

本轮改掉的两个真问题:

1. **`threadCreate` 要求栈页对齐**:`source/net/update_task.cpp` 里工作线程的栈原先只写了
   `alignas(16)`,libnx 直接返回 `LibnxError_BadInput`(`0x1759`,判定逻辑见
   `src/libnx/nx/source/kernel/thread.c`:"Verify alignment of provided memory")。
   现为 `alignas(0x1000)`。教训:这个错误只有真机才会暴露,主机侧测试与构建都不会发现。
2. **签名文件的名字**:App 取的是 `<清单 URL> + ".sig"`,发布脚本原先把产物写成
   `agent-manifest.sig`,两边对不上(线上表现就是"验签失败")。现统一为 `agent-manifest.json.sig`,
   工具、文档与镜像一致。

回归:改完跑 `tools/device-tests.py all`(t1a/t1b/t2/restore 四例全过)与
`tools/device-tests.py cycles --cycles 3`(三轮启动/退出都干净),外加 `make -C tests`(754 checks)。
本轮全部过程材料(镜像、证书、截图、日志)都在已忽略的 `build/scratch/` 下,不进仓库。

## 更新路径的三处修复(2026-09-20,真机验证)

## 路径缓冲规则补完(2026-09-20)

起因两条:上游把那条 libnx 报告移到了非公开仓库(链接不再可见,本仓库不再跟踪);同时拿到官方
SDK 的反编译证据 —— 官方客户端把路径拷进自己的 `FS_MAX_PATH` 零填充缓冲、装不下返回 `TooLongPath`
(6003),再按完整声明长度发出去(见 `docs/architecture.md` 第 4.2 节)。于是把"交给 `fs*` 的缓冲
必须自己盖住 `FS_MAX_PATH` 窗口"这条规则逐处核对了一遍,补上还漏的三处:

| 位置 | 原来 | 现在 |
|---|---|---|
| `source/log.hpp` 的 `Log::Sink::path` | `char[128]` —— 按 0x301 发出去时窗口越出数组 0x281 字节,只因 `Log` 是 `main()` 的局部(大栈映射)才没复发 | `util::FsPath::kBufferSize`(2 × `FS_MAX_PATH`),并用 `static_assert` 钉住尺寸 |
| `source/log.hpp` 的 `Log::Open()` | 在复制进 sink **之前**先用调用者的裸指针调 delete/create/open | 先 `util::FsPath`,三次调用与 sink 里的副本都用它 |
| `source/ui/app.cpp` 的开发开关(`dev-pause`) | 直接传字符串字面量 | 同样过 `util::FsPath`(字面量本来安全,收口是为了让规则没有例外) |

`util::FsPath` 自己也加了 `static_assert(kBufferSize >= FS_MAX_PATH, …)`,防止以后有人把缓冲改小。
刻意**没有**动的两处:`probe.cpp` 继续把裸指针交给 `fs*`(它的目的就是演示未保护指针的行为);
也没有对齐官方的 `TooLongPath` 返回值 —— 本应用的路径都是几十字节的固定串,超长只可能来自手工
放进卡里的开发清单,静默截断不影响正确性。

**验证**(`acnh-manager.nro` sha256 `77ed67d8…`,构建戳 `2026-09-20T05:16:28Z+72b366d-dirty+src:bdc00ef9`):
`make -C tests` 791 checks / 0 failures;`tools/check-i18n.py` 116 条同序;`./tools/build.sh` 零警告;
`tools/verify-release.py --nro` 36 项(含清单签名);真机 `device-tests all`(t1a/t1b/t2/restore)与

## 旧金手指冲突:检测从未触发与修复(2026-09-23)

现象:卡上一直躺着 `atmosphere/contents/01006F8002326000/cheats/FF1D1C05670DB602.txt`(6 118 B),
但首页、详情页都没有任何冲突提示,`log.txt` 里也从来没有 `legacy cheat present` 那一行 ——
用户实测反馈"manager 应该能检测到旧 cheat 文件,但机器上没看到提示"。

根因是**文件名判据写错了形状**。旧代码要求 `name.size() == 36`,即 32 个十六进制字符加 `.txt`;
而 Atmosphere 真正载入的金手指文件取的是运行中主模块号**前 8 字节**:

```c
sdmc:/atmosphere/contents/%016lx/cheats/%02x%02x%02x%02x%02x%02x%02x%02x.txt
```

(`stratosphere/dmnt/source/cheat/impl/dmnt_cheat_api.cpp` 的 `CheatProcessManager::LoadCheats`),
也就是 **16 位十六进制 + `.txt` = 20 字符**。真机卡上的名字正好 20 字符,于是那个条件永远为假:
这段代码从 2026-09-17(`e6e4a6b`)进仓库起,一次都没有命中过。

修复:

- 判据抽成不依赖 libnx 的 `source/env/cheat_file.*`(`IsLegacyCheatFileName`,16 位十六进制 +
  `.txt`,大小写都认 —— 卡是 FAT/exFAT,dmnt 用小写查、卡上是全大写也能命中),`detect.cpp` 改用它;
- **判据从"文件存在"改成"文件里确有条目"**:只要文件名对上就报警,会把整包无关金手指也算成冲突。
  真机卡上那份文件有 15 条,其中只有 `[聊天码生成到背包(最多10个)(X+十字右)]` 走聊天码通路,
  其余 14 条(体力值、复制槽位、清空、里程数)与 agent 无关,让用户为它们删掉整个文件是误伤。
  条目怎么认:`ChatCodeCheatEntry` 找**同时**读 `main+0x05255A60`(文字输入对象)与
  `main+0x5474040`(玩家链)的条目 —— 用代码而不是名字当身份,因为玩家会改条目名,而且名字里
  还带着激活键与个数,两样都会随指南版本变(地址语义见根目录
  `docs/text_spawn_to_slot1_guide.md` 的"关键地址")。成对判据是必要的:同一份文件里
  `[里程数最大 9999999]` 也读玩家链,但不读文字输入对象,只认一个地址就会把它误报;
- 主机侧新增 `TestCheatFile`(19 条):文件名 10 条(含卡上真实名字、dmnt 的小写写法、
  `toggles.txt`、旧的 36 字符形状哨兵)+ 内容 9 条(整包、改名后的条目、注释/花括号/CRLF/乱空格、
  带 UTF-8 BOM 的文件、只有玩家链的里程数条目、只有文字输入对象的条目、空文本、无条目)。
  带 BOM 那两条是实测补的:解析器原来会把 BOM 开头的第一行当成非条目行,于是**丢掉那一条的代码**;
  记事本默认就写 BOM,玩家改一下这份 txt 就能触发;
- 界面位置同时调整:这类漏看就会出错的消息移到**首页**状态行下方(琥珀色警告条),
  详情页保留同一行,理由见 `docs/architecture.md` §7 与 `AGENTS.md` 的文案原则;
- 警告条里给出的**是绝对路径而不是文件名**(`/atmosphere/contents/01006F8002326000/cheats/…`):
  只给文件名,屏幕上没有任何东西告诉玩家它在哪里;路径长了整整 42 个字符,于是这一行降到
  `kFontSmall`(18),`kHomeWarnHeight` 也随之由行高推导(= 行高 + 上下各 18),按钮位移
  `kHomeWarnShift` 同样由警告条几何算出来,不再是写死的 52;
- 警告三角按等边警告三角的比例画(底边比高多 1/5,`!` 在三角形内部居中):底边两倍于高度的
  画法在电视上是一条横向拉伸的形状,这个尺寸关系只能在真机上看出来;
- 文案说的是**代码**,不是文件:"检测到可能冲突的旧金手指代码" —— 文件躺在卡上不是问题,
  判据本身也只认带那条代码的条目;
- 配色是**琥珀橙**(`kWarn`,色相约 40°)而不是红:边框与三角用更亮的 `kWarnBright`(纯装饰),

而同一个构建的详情页写的是 `检测结果: supported build v3_0_3 (3.0.3)`、`清单来源: 随应用自带`。
根因:`ReportEnvironment` 用 `Evaluate(nullptr, …)` 求门控,并硬编码了"没有内嵌清单"那句话。报障时
要读的正是 `log.txt`,所以这不是措辞问题,而是日志在说假话 —— 构建明明带着发布物,它却说没有。

修法照界面的做法来:解析内嵌发布物(`payload::EmbeddedAvailable()` + `manifest::Parse`)再 `Evaluate`,
并打印这份清单的 agent 版本与 commit;没有导入发布物、或清单被校验拒掉时,如实写出原因。联网检查
在后面才跑、可能采用更新的清单,那一份由详情页与更新检查那两行负责,启动这两行只讲"这个构建带了什么"。

真机验证(构建戳 `2026-09-23T04:53:50Z+80ec96f-dirty+src:32e690c8`):

| | `log.txt` | 详情页 |
|---|---|---|
| 门控 | `gate: supported (supported build v3_0_3 (3.0.3))` | 检测结果 `supported build v3_0_3 (3.0.3) [install]` |
| 清单 | `manifest: embedded, agent 0.11.0 (commit c15e41858935)` | 清单来源 `随应用自带` / 联网检查 `清单可用, agent 0.11.0` |

## NSZ(压缩安装包)的安装:分节表 + zstd 流 + 分节再加密(2026-10-14/15)

现象(用户报):装卡上那份 `/.NSP/Super Mario Odyssey/[UPD][v1.4.1][0100000000010800][v393216].nsz`
时报"这个文件不是可安装的安装包",日志里是
`the package lists a content it does not carry: 55f840f5fe1ea70b536135659979a8f0`。原因:NSZ 把大的
NCA 换成了 `.ncz`(NCA 头原样 + 分节表 + 一段 zstd 流,分节里的数据是**已解密**的),而安装器只认
`.nca`,于是 CNMT 点名的那份内容"包里没有"。

**规则先在开发机上证明,再改代码**:按参考实现的布局(`nsz_dumper.cpp` 写 NCZ 的方式)与读侧语义
(`yati.cpp` 的 NCZ 解码 + `crypto.hpp` 的 `SetCtr/UpdateCtr`),把那份 `.ncz` 还原成 NCA 后,
`sha256` 的前 32 位正好是 CNMT 给它的内容 id —— 也就是说解码规则可证明:

```
sha256 55f840f5fe1ea70b536135659979a8f02fac6b59049a563bcdecfc2b4f8283a3
CNMT   55f840f5fe1ea70b536135659979a8f0     (内容 id = 整份 NCA 的哈希)
```

真机(相册 applet 模式,同一台机器):

| 步骤 | 结果 |
|---|---|
| 打开那份 NSZ 的确认页 | `SUPER MARIO ODYSSEY` / 1.4.1 / 更新 / **0.4 GB** —— 解压后的真实体积(卡上那份是 298.5 MB),分节表解析正确 |
| 传输中 | 第 2 / 4 个内容、当前文件名 `55f840f5….ncz`、0.25 / 0.37 GB |
| 结果页 | 「安装完成 / SUPER MARIO ODYSSEY 1.4.1(更新) / 已写入 microSD · 4 个内容 · 0.4 GB」 |
| `log.txt` | `install: finished stage=4`、`finish record read-back rc=0x0 contents=5`、`collect: ns app 0100000000010000 … 129:v=0x60000@5`(控制台把它当成该标题的第二条 meta) |
| **启动测试** | 启动 SUPER MARIO ODYSSEY(本体 + 这次装的更新)→ 进入游戏画面。也就是 NCZ 还原出来的那份 program NCA 被 loader 接受并执行了 |

这一轮踩到的两个坑都记在这里,免得后人重踩:

1. 第一版把负载偏移当绝对偏移用(漏加 `.ncz` 在容器里的起点),zstd 立刻报
   `the compressed content could not be decoded`;
2. 修好之后又报"流提前结束":判断"解码够了没有"时用的是**负载内**偏移,而调用方给的是**内容内**
   偏移,两者差 0x4000,于是解到尾部时永远差 16 KiB。修法是把"已解码到哪个内容偏移"统一成内容内
   偏移(从 0x4000 起)。

两个都在开发机上用同一份真实 NSZ 复现并验证过(探针脚本用引擎的同一套偏移约定;脚本属过程材料,
放已忽略的 `build/scratch/`)。

## 下载来源的实现与真机验证(2026-10-14/15)

下载来源(`Range` 探测 + 每次精确 Range 读 + 软键盘填地址 + 地址屏与两张停住卡)已经实现。真机看到:
地址屏、系统软键盘(预填 `http://`)、探测失败时停在地址屏并显示"先在系统设置里连上网络(手机热点或
同一个 Wi-Fi)"都正常;但**任何地址都连不上**,最早的怀疑("路由器客户端隔离")当天就被证伪:
真因是**下载来源从没初始化 BSD socket 服务**,是代码问题而不是网络问题(下面那段详述)。

**同时暴露并修掉的一处文案错误**:失败条原来把"连不上地址"写成"先在系统设置里连上网络"。这次实验里
主机**明明有网络**(同一天的 `log.txt` 里 `update check: manifest ok` 说明它成功出站过互联网),
只是连不上那个地址 —— 于是这条改成 `连不上这个地址,检查地址与端口是否正确`;真正"没网"的那一屏由
`nifm` 的前置检查负责,两处不再混用一句话。

**下载路径当时连不上任何地址 —— 根因是我们自己的代码(当天修掉,提交 `637ca45`)**:
我们把那份 337 MB 的测试包挂在局域网内的一个 http 服务上,服务端自测 206 + `Content-Range` 正常,
主机上地址也敲对了,可服务端**一个请求都没收到**。
我一开始把结论写成"这张网络的客户端隔离",**这个结论是错的**:用户用手机连同一个地址一测就通,
随后在代码里找到真因 —— **libcurl 的 Switch 端口只用 BSD socket,从不自己初始化这个服务**
(`net/http.hpp` 里写着这条),而当时只有"检查更新"那条路会 `socketInitializeDefault()`。于是同一个
进程、同一块屏上:**检查更新成功**(它初始化过)、**下载对任何地址都失败**(它从没初始化),
`curl` 只能报 "couldn't connect",被我们的代码翻成"连不上这个地址"。

修法:把服务做成**引用计数**的 RAII 会话(`net/socket_session.*`),`net::Get` 每次请求持有一个,
下载来源从探测持有到 `Close()` —— 两条路可能重叠,谁也不能把服务从对方脚下撤掉。同一轮还对齐了
**证书策略**:这一栈没有信任库,`net/http.hpp` 记着"验证关闭"(sphaira 与多数 homebrew 同样做法),
而下载来源当初漏了这两个选项、继承了 libcurl 的默认(验证开),于是只有它对自签名证书报错;
现在两条路一致,那张"证书无法验证"的卡(以及它的文案)已删除 —— 验证关着时那张卡只会是错的。

**修完之后的真机结果(全部以主机为 client,网关 192.168.8.1 的 nginx 为 server)**:

| 用例 | 结果 |
|---|---|
| T4 机制(HTTP) | 包放在网关 `/switch` 下,主机敲它的 https 地址 → **探测 206 + 区间读取** → 容器与 CNMT 解析 → **封面从包内读出** → 判定"已安装,跳过"(机器上已有这份 Lost Twins 2 1.0.1) |

**完整传输:先崩了一次,修好后走通(同一天)**。把这份包从机器上删掉(这样不会再走"已安装,跳过"),
再次下载安装 —— 主机**整机崩溃**(Atmosphere 的崩溃提示屏)。取证与结论:

- `sdmc:/atmosphere/crash_reports/01792057938_010000000000100d.log`:进程 `hbloader`(就是我们这栋
  NRO)、`Data Abort`、fault address `0x1`,寄存器里赫然是 `Content-Range` 的文本
  (`" bytes 337…/337152800` + CRLF);把 PC/LR 与调用栈在本地 ELF 上符号化
  (`aarch64-none-elf-addr2line`)得到:
  `GameInstall::Step → ReadCompressed → curl_easy_perform → Curl_http_readwrite_headers →
  Curl_client_write → 我们的 OnHeader → std::string::assign`。
- **根因**:`CURLOPT_HEADERDATA` 被设成 `Open()` 里的**栈局部对象**,而 libcurl 会在**这个 handle 的
  每一次请求**上都调用它(传输期间每一次区间读都要重新解析响应头)。`Open()` 一返回那对象就死了,
  于是 libcurl 一直往一个野指针写 `Content-Range` —— 栈被写坏,最终数据异常。跳过态之所以前几次都没炸,
  是因为读的次数少、野指针恰好落在还"能用"的栈上;这次读得多了就踩爆。
- **修法**:把响应头的接收目标做成 `HttpSource` 的成员,活到 `Close()` 为止(提交 `installer: the header sink must outlive Open`);
  同族教训记在设计文档第 11 节:`libcurl 会长期持有我们交给它的指针`。
- **复验(与崩溃时同一套配置:主机直连网关 nginx(自签名)→ 同一个包)**:确认页
  「开始安装 / Lost Twins 2 / 1.0.1 / 本体 / 0.4 GB / microSD」→ 按 `A` →「正在接收 / 第 2/3 个内容 /
  28%」→ **「安装完成 / 已写入 microSD · 3 个内容 · 0.4 GB」**;桌面上出现 Lost Twins 2 的方块;
  `log.txt` 里 `finish tickets 1 of 1 imported`、`record read-back rc=0x0 contents=4`、
  `finished stage=4` 齐全,**没有再崩**。
- 顺带确认:`/Nintendo/Contents/placehld` 在成功安装后是空的 —— 崩溃那次的占位**随重启被系统清掉**
  (占位不跨重启),所以没有留下空间泄漏;这也说明"中断续传"真正要覆盖的是**不重启**的情形(第 10 节)。

### 追查到根因:记录里那份 meta 不是"这次安装的那一份"(2026-10-15)

用户复验:sphaira 与 DBI 装同一个 XCI 都能正常启动,所以不是卡带加密的事,是我们代码的错。日志里
我们自己的自检先说了真话:

```
install: usable? storage=5 rc=0x0 contents=5 sized=1 control=1 present=0
install: usable? missing 1 of 5: 6dad0a38d832e2ce4c50784151891653
install: meta candidate 6dad0a38…cnmt.nca type=dlc
install: meta candidate 92974ca9…cnmt.nca type=base
```

`6dad0a38…` 是整合包里**某个 DLC 的 meta**,而我们的安装从没装过它。原因是两处不一致:纯解析层
(`ReadPackage`)把 `meta_content_name` 记成**容器里第一个 `.cnmt.nca`**(整合包里通常是 DLC 的),
而设备侧虽然按类型选对了本体,却**没有把这个名字写回去** —— 写进 ncm 的 meta 记录第一项于是指向
一份不存在的内容,控制台据此把整条记录判成不可用,标题拒绝启动。单 meta 的包(NSP/NSZ)走不到这条
分支,所以此前一直全绿。

修法:选完本体后把 `meta_content_name` 改成选中的那份(并把这个选择写进日志:`install: primary
meta …`、`install: installing meta …`)。

### 同时按参考实现补上"容器里有几份 meta 就装几份"(2026-10-15)

sphaira 的 `InstallInternal` 是遍历容器里每个 CNMT 逐个安装(本体、更新、每个 DLC,各自一份记录);

界面确认页的「类型」会把搭车的写出来(「本体 + 更新 ×1 · 追加内容 ×2」),名称/版本取**生效版本**
那份 meta 的控制数据,agent 的支持判断也改用它(真机复验由用户执行:卡上 `/.NSP/luigi.xci` 整份安装,

## XCZ(压缩卡带镜像):块表与原样块,第一次真机安装失败与修复(2026-10-15)

素材:用户手上的 `Super Mario Party Jamboree [0100965017338000][v0][US].xcz`(5 595 285 654 字节;
主机在 `/.NSP/` 下一份,开发机在 `~/Downloads/games/超级马里奥派对:空前盛会/xci本体/` 一份,同一文件)。
用户手头一直没有样本,所以此前只做过代码层自检(结论与补丁见设计文档第 34 条),真正的问题要到这份
文件上手才暴露出来。

**格式结论(有出处)**:XCZ 的压缩只发生在**文件**这一层 —— 参考实现的 dumper(`NszExport`)逐文件写出,
只把 `Program` / `PublicData` 类型的 `.nca` 换成 `.ncz`,其余(分区头、HFS0 表、meta、control、legal)
原样;它的 XCI 解析器对 `.xci` 与 `.xcz` 用同一段代码读分区表,即分区表必须是明文。所以我们的解析路径
(root HFS0 → `secure` 分区 HFS0 → 其中 `<contentid>.ncz` 条目 → NCZ 表 → 解码 + 分节再加密)与 NSZ 同源;
代码层自检先补齐的三处(压缩的 meta/control 也能读、`.cnmt.ncz` 名字能被识别、解码后的真实大小改用 NCA
头里声明的 size)见设计文档第 34 条。

真机现象:确认页正常(名称/封面/版本 1.0.0/本体/5.6 GB),传输阶段报
`transfer failed: the compressed content could not be decoded`,而同一个文件 sphaira 装得上、能运行。
日志里表解析、体积、元数据全对:`meta 1427c6a5…cnmt.nca title=0100965017338000 v=0x0 type=base
contents=3`、`e0s=5679267840`、`control content: ok`,只有解码那一步失败。

**根因**:我们此前把整个负载当成**一条** zstd 流喂给 `ZSTD_decompressStream`,而这份包的负载带**块表**,
里面**混着原样存放的块**:

| 项 | 实测值 |
|---|---|
| 块表 | ver 2 / type 1 / 块大小 2^20 = 1 MiB / 5417 块 / 声明解压总量 5 679 251 456(= NCA 大小 − 0x4000) |
| 分节 | `0x4000..0x1C000`(crypto 1,原样)、`0x1C000` 起与 `0x151010000` 起(各带自己的 key/counter,AES-CTR) |
| 块 0(压缩) | 945 448 → 1 048 576 |
| 块 1、2…(原样) | 1 048 576 = 1 048 576(压缩没变小,dumper 写原字节) |
| 末块 5416(压缩) | 113 843 → 163 840(= 5 679 251 456 mod 1 MiB) |

块 0 那条帧解得很干净,所以 zstd 不报错;到块 1 开始把**原样字节**当帧头读,才报
`could not be decoded` —— 这也解释了为什么"所有表检查都通过"却装不上。参考实现的读侧
(`sphaira/source/yati/yati.cpp` 的解码线程)正是这么做的:按块找当前块,
`decompressedBlockSize = 1 << block_size_exponent`(末块取声明总量的余数),
`compressed = 块在文件里的体积 < 该块解压后的体积`,原样块直接拷贝、压缩块才走 zstd;
我们此前只解析了块表、解码时没用它。修复与规则见设计文档第 35 条。

**开发机上先证明,再上真机**(两条互不相干的路径解同一份真实文件;两个工具都已入库、登记在
`docs/tools-guide.md`):

| 路径 | 结果 |
|---|---|
| `tools/ncz-probe.sh <xcz>`(应用自己的 C++ 代码:`container.* / ncz.* / ncz_decode.*`) | 5 679 251 456 字节,sha256 `8b4fcc9c…23fe498`,5417 块逐块通过"解出字节数 = 表里声明的数" |
| `tools/ncz-blocks.py <xcz>`(自带容器解析,逐块调 `zstd`) | 同样 5 679 251 456 字节、同样 sha256 |

主机测试另加了自造的"压缩块 + 原样块 + 半块尾块"混合包与"无块表整段流"两种形态(测试现在也链 zstd),
专门钉住"原样块必须拷贝"这条规则 —— 这正是漏掉的那条。

**留给用户真机验收的清单**(与 XCI 那次一致,差别只在"解码"这一步):

1. 用卡上 `/.NSP/Super Mario Party Jamboree [0100965017338000][v0][US].xcz` 走一遍本机文件安装;
2. 传输页应能走过开头这一段(此前刚解完第一个块、进入第一个原样块就报 `could not be decoded`,
   也就是 5.6 GB 里大约 1 MiB 处),进度条按**解压后**体积推进;
3. `log.txt` 里不应再出现 `the compressed content …` 一类失败行;
4. 装完能启动,控制台显示的版本与生效版本一致;同一个文件用 sphaira 再装一次作为对比项。

## 四格式对照参考实现的一轮审查(2026-10-15,代码层,离线可验)

背景:四种格式(NSP / NSZ / XCI / XCZ)此前都有过"参考实现能装能跑、我们不能"的记录,而参考实现
(sphaira)就在本工作区里。这一轮把四种格式的路径逐段对照它的安装/收尾序列(`yati.cpp`、
`container/nsp.cpp`、`container/xci.cpp`、`nx/nca.hpp`、`nx/ncz.*`),并把可疑处拿到真实样本上核实。

**样本实测(读每个内容的 NCA 头:取该内容的 0xC00 字节,用 `SDcard/switch/prod.keys` 的 header key
按 NCA 头的 XTS 布局解密——`tools/parse-nsp.py` 的 `aes_xts_decrypt` 就是这段——再看 0x204 的分布位、
0x208 的 size、0x230 的 rights id;容器条目清单可用 `tools/ncz-blocks.py` 列出)**:
四种格式的**每个内容**都满足
`header.size == entry.size`(容器条目没有 padding),所以"内容大小用哪个"在现有样本上是同值;
`[UPD][v3.0.3][01006F8002326800].nsp` 与 `[UPD][v1.4.1][0100000000010800].nsz` 的 **program 内容带
rights id**(标题密钥加密,靠随包的 `.tik`/`.cert` 解),其余内容是标准加密;`luigi.xci` 全部
`rights_id = 0` 且多数内容 `distribution = 1`(卡带,靠 distribution 位改写才能从 SD/NV 启动);
`Super Mario Party Jamboree.xcz` 的 program 内容 `rights_id = 0`、`distribution = 1`,与前一份
`.xcz` 的规格一致。

据此修了四处、并纠正一条跳过语义(规则与理由见设计文档第 36 条):

| 差异 | 后果(修之前) | 现在 |
|---|---|---|
| 记录里的"所需系统版本"没清零 | 面向更新固件的包装得上、**启动被系统拒绝**("需要系统更新") | 按参考实现默认清零(application / patch) |
| 只读第一份 `.tik`/`.cert` | 容器带多份票时,后面的标题密钥拿不到 → 装完启动失败 | 按 rights id 成对收全、全部导入,缺证书直接拒绝 |
| 内容大小取自容器条目 | 条目带 padding 时会写入"记录没描述的内容" | 以 NCA 头为准(不一致时按头走并写日志) |
| meta 内容不改 distribution 位 | 与参考实现装出的字节不同(今天仍能挂载,实测) | 两条写路径共用同一个头改写 |
| "已有更高版本就跳过"对四种类型都生效 | 本体内容被删、更新记录还在时,装本体被跳过,**标题永远修不回来** | 只对**更新包**生效(与参考实现一致);本体/DLC 照装,启动版本仍取最高 |

有意保留的一处差异:参考实现默认打开的"票转公共票"(`convert_to_common_ticket`)不做。它实际做的事:
**公共票**先用随包证书链里的公钥验签,验得过就原样保留(官方渠道的包都是这条,整步是空操作);
**个人票**才用本机 setcal 的设备密钥 RSA 解出标题密钥,改写成一张 issuer 为 `Root-CA00000003-XS00000020`、
签名块填 0xFF 的"假公共票"。所以 **prod.keys 与官方票无关**——只有个人票这条路会用到它(setcal 交出的
设备密钥本身是被 `eticket_rsa_kek` 加密的),而真正离不开 keys 的是默认关闭的
`convert_to_standard_crypto` / `lower_master_key`。本 App 原样导入票:官方包与参考实现结果一致(ACNH 的
更新包就是这么装的,实机可运行);个人票交给 `es` 判断——为本机签发的通常照用,来自别的主机的谁也救不了
(转公共票用的也是**本机**设备密钥,device id 不匹配同样失败)。日志里的 `tickets N of M imported` 与
`a content needs title key …` 是判别依据。

## 下载吞吐:实测数据与由此定下的配置(2026-10-16)

测试条件:主机直连网关(192.168.8.1 的 nginx)取同一个 337 MB 的 NSZ,主机侧 dev-aid 计时层记录
每阶段耗时。**结论:传输已跑在链路速率上,限制因素只剩链路本身。**

**改进前后**(同一个包、同一条地址):

| | 解码在读线程 | 解码在写线程(定稿) |
|---|---|---|
| 整轮安装 | 54.9 s | 33.8 s 传输循环 + 收尾,约 38 s |
| 传输循环 / 网络段 | 51.2 / 46.4 s(**7.3 MB/s**,均 572 ms/请求) | **33.8 / 33.7 s(10.0 MB/s,均 406 ms)** |
| 解压 / 写占位 | 3.4 s / 10.6 s | 3.5 s / 13.9 s |
| 流水线等待 | 写等读 35.2 s、读等写 0.3 s | 写等读 13.3 s、读等写 0.0 s |

网络段 +37%、传输循环 −34%,比"省下 3.4 s 解压"多得多:取数线程不再与解码、写盘抢 CPU 与内存带宽;
它的每请求耗时降到与纯下载探针持平 —— **网络占传输循环的 99.7%**,而 10.0 MB/s 正落在同一地址纯下载
探针测到的区间内。

**网络探针(同一地址,libcurl 直测,每种形状 64 MiB)**:TLS 单流(不带 Range)12.1 MB/s、4 MiB Range
×1 11.9 MB/s、4 MiB Range ×4(四连接)13.1 MB/s、1 字节 Range 请求延迟 20 ms。同一形状跨轮次会在
8.9~13.1 MB/s 之间浮动 —— 链路本身的抖动比任何代码差异都大。

### 为什么这样配置(每条都有实测依据)

| 配置 | 依据 |
|---|---|
| 4 MiB 块,不改成 8 MiB | 1.86 GB 包实测:4 MiB 183.5 s / 10.1 MB/s,8 MiB 207.7 s / **9.0 MB/s**(请求数 445→223,但每次 412→930 ms)——更慢,已撤回 |
| 单连接 Range,不做并行 | 1.86 GB 包同一轮内:TLS 4 MiB Range ×1 **7.3 MB/s**,×4 四连接 **7.4 MB/s**(+1.4%,即零);单流不分块 7.9——链路已饱和,与连接数无关 |
| 每请求固定开销约 20 ms | 1 字节 Range 平均 21 ms,占每次 4 MiB 请求(约 548 ms)的 ~4% |
| TLS 照常,不做降级 | 同一份文件分别用明文 http 与 https 测,两者同速(6.6 对 6.8 MB/s);mbedTLS 不是瓶颈 |
| 取数线程只做网络读取,解码+写占位在写线程 | 见上表:7.3 → 10.0 MB/s |
| 不加第三条线程 | 写线程整轮仍空 13.3 s |

**验收**:装完 Lost Twins 2(3 个内容 0.4 GB)桌面出现图标、启动进入游戏配对画面 ✓。

### 这一轮修掉的两个真 bug

1. **重复推进**:`WriteRange()` 内部已调 `Advance()`,新写路径又调一次 → 任务计数领先解码器,最后一块写到内容末尾之后(`0x00307202`,`content offset == content size`)。
2. **预写好的内容被重新取数**:meta 与 control 在 `Prepare` 阶段已写满并标记 `written = size`,旧循环靠 `NextRange()` 跳过,新循环只看 `skipped`。判据补上 `written >= size`。

测法本身留在仓库(开发辅助,发布构建编译为空):`source/install/dev_stats.*` 的计时层与
`source/probe.cpp` 的 `RunNetworkProbe`(开关 `/switch/ACNH-Manager/dev-netprobe`,地址取 `dev-netprobe-url`)。

## 启动时间与"选包到卡片"的耗时:拆开看(2026-10-16)

两处卡顿都被量过,结论是**都不是测试版的问题**(开发构建与发布构建做的是同一份工作;开发期专用件只在
SD 上有开关文件时才跑)。计时是开发辅助:`install/dev_stats.*` 的 `launch:` / `prepare:` 行(发布构建
里这两行连同计时一起消失)。

**启动:第一帧 4.87 s → 1.12 s,可用(首帧 + 启动日志写完)5.15 s → 1.63 s**。下面是三轮实测的
同一组 `launch:` 标记(同一个包、同一台主机、同一条启动路径;数字是"距 `main()` 第一行的毫秒"):

| 阶段 | 改之前 | 只修"重复采集 + 报告挪到首帧后" | 再把两处日志改成一次写(定稿) |
|---|---|---|---|
| fs + SD + log 就绪 | +79 | +77 | +76 |
| 字体就绪 | +2613 | +659 | +635 |
| framebuffer 就绪 | +2793 | +844 | +811 |
| 环境采集与计划 | +4419 | +2523 | **+970** |
| **第一帧(黑屏结束)** | **+4873** | +2678 | **+1119** |
| Init 返回(可交互) | —— | +3068 | +1485 |
| 启动日志块写完 | —— | +3229 | **+1629** |

三处原因,按发现顺序:

1. **环境被采集了两遍**:启动器为了写 log.txt 的 `== ACNH-Manager ==` 那一块先 `env::Collect` 一次,
   `App::Init` 又采一次同样的东西(各约 1.6~2.2 s)。现在只采一次,报告由 App 从这一次采集里写出来
   (`App::TraceEnvironment`)。
2. **那一块日志写在第一帧之前**:每行日志都是"开→写→flush→关",而且两个 sink(`log.txt` +
   `log-history.log`),60 行约 2.2 s。现在它挪到第一帧之后、第一次循环迭代里写 —— 内容一字不差,只是
   来得晚一点。
3. **真正的大头是"每行一次文件操作"本身**:实测约 37 ms/行(两个 sink),所以
   ①报告块 60 行 = 2.2 s、②环境采集那 48 行 = 1.5 s。修法是把"一组该一起写的行"合成**一次写入**:
   `Log::Block`(报告块,2.24 s → 0.16 s)与 `Log::BeginBurst`/`EndBurst`(`App::Collect` 那一趟,
   1.71 s → 0.16 s)。搬走报告块之后,那 2.2 s 从"黑屏里看不见"变成了"画面出来了但两秒不响应",
   所以第 3 条不只是省时间,也修掉了这个更难受的手感。

   这条经验适用于本仓库所有"一次动作写一簇日志"的地方:打包安装包(§ 上面那条 `prepare:`)也是同一个
   毛病 —— 0.83 s 里 0.5 s 是日志。传输循环里**没有**逐片日志(一次安装只写几行),所以下载/上传的
   吞吐不受它影响。

剩下 1.12 s 的去向:**字体初始化 0.56 s**、framebuffer 0.18 s、环境采集 0.16 s、首帧绘制 0.15 s、
fs/SD 0.08 s。也就是说下一块要动的只有字体(加载系统共享字体 + FreeType/HarfBuzz 初始化),那属于
另一轮工作。

**对照 `main` 分支的构建**(同一个方法:从相册启动、外部采屏;`main` 的代码没有 `launch:` 标记,
所以只能外部计时):界面出现在 **+2.1~2.5 s** 之间 —— `main` 既没有重复采集的修复,也没有这两处
批量写,所以它把这两笔都付掉了。**当前分支的开发构建第一帧 1.12 s、发布构建(日志默认关)约 0.8 s**,
两者都已经快过 `main`,而开发构建还写着日志。

**剩下的日志成本,与写不写的运行时开关**:批量写之后,启动时还剩大约十条"单独出现"的行(每行都是
"开→写→flush→关",两个 sink,约 37 ms),合计约 0.35 s —— 这是"逐行落盘、随时可被 FTP 读走"这条纪律
本身的价钱,不再是一次大块的浪费。要连这一块也不付,就靠启动时的运行时开关(`source/log.hpp` 的
`LogWanted`,在 `main` 里读一次):**开发构建一律写**;**发布构建只在卡上有 `/switch/ACNH-Manager/log-on`
时才写**(存在即可,不看内容)——已发布的二进制不用重编就能打开日志,默认那份则完全不写。

**真机验过三种组合**(2026-10-16,发布构建 `+release` 与开发构建 `+devaids` 各一次):

| 构建 | 卡上 `log-on` | 结果 |
|---|---|---|
| 发布 | 无 | `log.txt` **逐字节未变**(启动前后 sha256 相同)—— 没创建、没截断、没写一行 |
| 发布 | 有 | `log.txt` 被重建成那一轮的日志,首行是这次启动的 `build: …+release` |
| 开发 | 无 | 照常写(首行 `build: …+devaids`,并带 `launch:` 计时行)—— 开发循环读的就是它 |

**关掉的实测效果**(同一台主机、同一条启动路径,外部采屏;关日志时读不到 `launch:` 行,所以只能采屏
计时):关日志那一轮,第一帧出现在**+0.62 s(还是黑)与 +0.90 s(已出界面)之间,即约 0.8 s**;
开日志的开发构建按内部计时是 +1.12 s。

**"选中安装包 → 开始安装卡片"的延迟:0.83 s → 0.22 s**(同一个包的实测;`prepare: 221 ms total (meta
reads 76, control 124, queries 1)`)。原因和启动那边是同一个:
`prepare: 831 ms total (meta reads 48, control 251, queries 292)` 里,控制内容那一段 0.25 s 中约
0.15 s 是它在写自己的 4 行日志、两条存储的版本查询 0.29 s 中约 0.22 s 是那 6 行日志 —— 也就是说
**0.83 s 里有 0.5 s 只是把诊断行一行一行写到卡上**。`Prepare` 现在用同一个突发机制(`LogBurst`,RAII,
因为这条路径有十来个提前返回),整段日志随函数返回一次写出,于是 `prepare: 181 ms total (meta reads 54,
control 107, queries 0)` —— 剩下的 181 ms 才是真正的工作(读 meta、挂载控制内容读 NACP 与封面、
问两条存储的版本)。


## 未完成的安装:真机走通一遍(2026-10-16,§10)

场景是**下载来源的中断**(设计里最要紧的一种):本机 `tools/serve-package.py` 提供 Overcooked Special
Edition 的 785 MB NSP,主机在地址屏输入地址、确认、开始接收,到约 18% 时**把服务端杀掉**,然后在主机上
继续操作。证据链(采屏 + `log.txt` + 卡上的 `install-task.json`):

| 步骤 | 结果 |
|---|---|
| 传输中断 | 结果页「安装失败 / the source stopped early (connection lost or file truncated) / **未完成的安装已保留,下次进安装页可以继续**」;`install-task.json` 886 字节:`source=http-client`、`target=sd`、`url=…`、程序内容 `written=138412032`(132 MiB,正好是两次 64 MiB 刷新) |
| 重开安装页 | 直接进「未完成的安装」屏:`已接收 139 MB / 748.8 MB`、`占位 748.1 MB`,三个入口 `A 继续 / X 放弃并清理 / Y 选择新的安装内容`;数字是**问控制台问出来的**(同一轮的日志里是 `console holds 138412032`) |
| 按 `A 继续` | 重新打开同一个 URL(又一次 Range 探测),确认页照常;`log.txt` 写 `install: resume: 2 continued, 1 finished, 0 started over` |
| 装完 | 结果页「安装完成 · 3 个内容 · 0.7 GB」,`finish returned 1 stage=4`(Done);**`install-task.json` 已消失**;桌面出现该游戏 |
| 另一条路(放弃) | 早前那次中断的任务按 `X 放弃并清理` 后:文件被删、页面回到三入口屏(那次的占位已被重启清掉,所以空间没有变化) |

**真机才知道的三件事**:

1. **重启会清空占位**:同一次中断后重启主机,空闲空间从 72.5 GB 回到 77.7 GB —— 5.2 GB 的占位没了。
   所以"重启后继续"实际是从头开始(屏幕会明说"占位已被系统清理:继续会从头开始"),而"应用被杀 /
   断网"这类**没有重启**的中断才能接着写。这条写进了设计文档第 10 节。
2. **续传用的数字必须问控制台**:文件里写着"已接收 1.0 GB"而占位早就没了,直接照抄就是骗人;现在进
   「未完成的安装」屏时逐个 `HasPlaceHolder` 校验,只把真的还在的算进去。
3. **两个只有真机会暴露的 bug**(都已修):
   - 离开结果页(`B`)会走 `LeaveInstallScreen()`,那里把"还没装完的包"一律 `Abandon` —— 于是刚说
     "已保留"的任务,一按返回就被删掉了。现在引擎用 `KeepsTask()` 说明"这次运行的任务文件必须留住",
     那种情况只清掉"只是为了读而建的占位";屏幕离开时还留一行 `install: left the screen (stage=…,
     task kept=…)` 便于日后复核。
   - 续传时,"这次运行已经读进占位"的 meta / control 内容会被文件里更旧的记录覆盖成 `written = 0`,
     而 `Begin()` 随后又要给它们建占位 —— 系统拒绝(同一内容已经有占位),安装直接失败。现在
     `AdoptResume` 跳过这些已经完整的内容。

**还没验的**:**上传来源**的续传(M4 才有上传来源;本机文件与下载两条来源的续传都走过了)。

## HTTP 服务端与网页:第一片真机验收(2026-10-16)

服务端薄层(`source/net/http_server.*`)与自包含网页(`data/installer_page.html.bin`)的第一片:页面能
被打开、状态能读、地址能提交、取消会被拒绝、生命周期跟着安装页走。证据是"从开发机 curl 主机" +
`log.txt` + 主机采屏(**主机的地址与端口 4321 从日志里读**):

| 手法 | 结果 |
|---|---|
| 进安装页(`＋`) | 日志:`http: listening on port 4321` + `http: page ready at http://192.168.8.160:4321`;离开安装页(`B`):`http: the page server stopped` |
| `curl http://192.168.8.160:4321/` | 200、12090 字节的 `text/html`;页面里 `const L = {…}` 是**当前语言**的 28 条文案(当时界面是中文),`__ACNH_LABELS__` / `__ACNH_LANG__` / `__ACNH_ADDRESS__` 三个标记都被替换掉,没有残留 |
| `curl …/status.json` | `{"schema":1,"state":"idle",…,"pending":null}` —— 页面靠它决定显示哪一屏,自己不留状态 |
| `POST /url`(正文一个地址) | 200,主机的日志:`install: the page submitted an address; opening it as a download` → 下一帧就走普通下载那条路(Range 探测失败时地址屏照常报错)。这条就是设计里"手机粘网址"的主入口 |
| `POST /cancel`(没有任务时) | 409 + `nothing to cancel` —— 页面据此显示"主机没有接受取消请求" |
| `POST /upload` | 501(数据通路还没接;用它而不是 404,是为了让"这个服务器还不会做这件事"和"这个路径它不认识"分得清) |
| 未知路径 | 404 |
| 把界面语言切成 English 后再取页面 | `lang="en"`、`"pageStep1":"Step 1 - pick the file to install"` —— 页面文案确实来自 i18n 表,跟着 App 的语言走 |

一条到手才发现的小 bug:`nifmGetCurrentIpAddress` 交回的是**网络字节序**,第一版把四个字节手工拆开,
日志里立刻印出 `http://160.8.168.192:4321`(`192.168.8.160` 的反序);改成 `inet_ntop` 后正确。
